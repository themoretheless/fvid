# Fvid resident GPU против FFmpeg

Фактические замеры на Apple M4 Max / macOS. FFmpeg 9.0.1. Завершены 2026-09-04T23:23:55.037374+00:00.

**Результат:** Metal-цепочка из трёх этапов медленнее FFmpeg default в 1.70–2.09 раза. Объединённый CPU Fvid быстрее FFmpeg default в 1.32–2.66 раза. Это результаты конкретного полного CLI-сценария, не универсальное сравнение движков.

## Медианное время, миллисекунды

Каждый вход содержит 60 кадров YUV420p. Все операции сохраняют точные сэмплы выбранной области. Crop уменьшает ширину и высоту вдвое; вторая последовательность применяет его после hflip.

| Вход / последовательность | CPU Fvid, объединённый | Metal, объединённый | Metal, 3 resident-этапа | FFmpeg default | FFmpeg 1 thread |
|---|---:|---:|---:|---:|---:|
| 1280x720 / crop → hflip → vflip | 10.43 | 48.90 | 52.26 | 26.46 | 27.40 |
| 1280x720 / hflip → crop → vflip | 10.37 | 49.94 | 54.92 | 27.62 | 44.53 |
| 1920x1080 / crop → hflip → vflip | 17.17 | 60.52 | 68.23 | 32.68 | 39.27 |
| 1920x1080 / hflip → crop → vflip | 16.80 | 61.69 | 66.93 | 34.20 | 73.68 |
| 3840x2160 / crop → hflip → vflip | 52.55 | 110.18 | 117.69 | 69.23 | 99.43 |
| 3840x2160 / hflip → crop → vflip | 53.62 | 108.54 | 128.72 | 71.46 | 223.78 |

Для объединённого Fvid-прохода координата crop пересчитана при hflip → crop; эквивалентность подтверждена сравнениями всех выходных кадров. Сравнение использует наиболее прямую реализацию каждого движка, не заставляет CPU Fvid создавать три отдельных процесса.

## Методика

- 6 сценариев × 5 вариантов × 7 измерений = **210 измеренных запусков**. Дополнительно один прогрев каждого варианта и 30 полных проверок выходного файла до измерений.
- Порядок вариантов случайный в каждом раунде, seed 20260905. Измеряется медиана; все отдельные времена, минимум/максимум и порядок запусков сохранены в JSON.
- Входной файл общий для вариантов, файловый кэш прогрет. Во время измерений Y4M записывается в null sink.
- Включены запуск процесса, подготовка GPU/device/pipeline, чтение, upload, фильтры, readback, сериализация. Не включены генерация входа и проверка результата. Это не kernel-only benchmark, не измерение дисковой записи/fsync и не транскодирование.
- FFmpeg default — основной baseline с обычными CPU-фильтрами crop/hflip/vflip. Ограниченный одним потоком FFmpeg показан отдельно; GPU-фильтры FFmpeg здесь не измерены.
- Для каждого конкретного входа проверены SHA-256 всех 60 кадров во всех пяти вариантах. Каждая измеренная Metal-команда обязана сообщить backend=metal; fallback не допускается.
- Resident-цепочка в каждом запуске сообщает 60 uploads, 60 downloads и 180 filter passes. Между этапами host transfers отсутствуют по реализации и счётчикам API; аппаратной трассировки traffic counters нет.

## Что это означает

Удержание промежуточных кадров на GPU работает, но три прохода не выгоднее уже существовавшего объединённого Metal-прохода для этих операций. Возврат конечного результата в RAM и создание pipeline остаются частью задачи; вклад каждой стадии отдельно не профилировался, поэтому замер не доказывает конкретную причину проигрыша.

Сравнение трёх resident-этапов с объединённым проходом не изолирует эффект удаления readback: число shader passes отличается. Не заявляем ускорение относительно прежнего однопроходного GPU-фильтра. Здесь также нет аппаратного decode→filter→encode, CUDA-измерений, оценки долгой работы, энергии или независимых доверительных интервалов.

## Воспроизведение и доказательства

```sh
cargo build --release
python3 scripts/benchmark_resident.py --frames 60 --rounds 7
```

Запуску требуется доступ к физическому Metal GPU. На этом хосте sandbox скрывает устройство; измерения выполнены с доступом к GPU.

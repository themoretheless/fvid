# Negative Matroska subtitle frames

RFC9559 section11.2 discourages negative final frame timestamps but requires readers encountering them to decode the content without playing it. This applies even if the frame duration extends beyond zero. Reference: https://www.rfc-editor.org/rfc/rfc9559.html#section-11.2 . No source example was copied.

The native reader previously clamped negative subtitle PTS tozero and then added the full BlockDuration. Wholly negative text appeared at the start of playback, and a crossing-zero negative frame also became visible. This is a separate format/presentation rule from MP4 signed-span clipping (FVID-0422), with a different acceptance expectation. The final original-source repro also verifies the exact40ms interval of the actual picture chosen by every seek; the same1pass2fail remains.

Nine exact packet snapshots, both parser ownership paths and continuous picture/clock/EOF parity establish that hidden text is not caused by an unrelated parse or decode refusal. Actual software video seeks check the expected selected picture interval and the exact active-caption content at gaps and exclusive boundaries. These are accepted files with suppressed negative content, not whole-file refusal tests.

The correction occurs after reading and decoding each caption. Negative PTS prevents publishing a visible Cue; positive timestamps and existing explicit/fallback clocks keep their behavior. No public API, parser, codec, CodecDelay policy or performance policy changes. CodecDelay adjustments and physical-device subtitle rendering are outside this finite qualification. Generation is offline pure Python, separate from ordinary tests; no FFmpeg, network or private media/parameters are used. All codecs/sign variants and repeated checks count as one improvement.

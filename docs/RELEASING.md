# Релизы

Используется схема airbug: версия в корневом `Cargo.toml`, тег `fvid-vVERSION`,
GitHub Release с автоматически собранными заметками и постоянная ветка `release`
для Git-зависимостей. Версия относится ко всему репозиторию fvid.

## Выпуск

1. Обновить версию пакета `fvid` в `Cargo.toml` и `Cargo.lock`, влить в `main`.
2. Проверить Linux и Windows CI на выпускаемом коммите.
3. Запустить **Actions → Release → Run workflow** на `main` и указать точную версию:

   ```sh
   gh workflow run release.yml --ref main -f version=0.1.0
   ```

Workflow проверяет совпадение версии с Cargo, создаёт аннотированный тег и GitHub
Release, затем передвигает `release` на коммит тега. Существующий тег допустим только
на том же коммите; повторный запуск продолжает выпуск без пересоздания релиза.
Стабильные версии выпускаются с `main`. Версия с суффиксом SemVer, например
`0.2.0-rc.1`, создаёт prerelease и может выпускаться из другой ветки, как в airbug.

Вручную отправленный тег `fvid-v*` тоже обновляет `release`, если соответствует
версии Cargo. Этот путь обновляет только ветку; GitHub Release создаёт workflow
**Release**. Для тегов, созданных через `GITHUB_TOKEN`, обновление ветки выполняется
в самом Release workflow: такие push-события не запускают другой workflow.

Ветка `release` движется только вперёд. Старый или расходящийся тег её не перезапишет.
При отказе этого шага тег и GitHub Release могут уже существовать: сначала проверить
их SHA и историю `release`, затем повторить выпуск на подходящем коммите.

## Подключение

```toml
fvid = { git = "https://github.com/themoretheless/fvid", branch = "release", default-features = false }
```

Для фиксации версии вместо `branch` использовать `tag = "fvid-v0.1.0"`.
Workflow выпускает исходники через GitHub Release; бинарные сборки и публикация
на crates.io в этот процесс не входят, как и в основном release workflow airbug.

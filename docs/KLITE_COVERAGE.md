# Покрытие кодеков K-Lite Codec Pack

Проверка того, что fvid декодирует набор форматов, который K-Lite Codec Pack считает своим
продуктом. Это измеримая надстройка над `docs/FEATURE_MATRIX.md`, а не пересказ
`ffmpeg -codecs`.

## Как измеряется

Обычный `python3 scripts/validate_klite_coverage.py` запускает нативные Rust-тесты
и проверку зависимостей без внешнего oracle. Отчёт —
`benchmarks/native-klite-validation.json`; это не новый замер строк матрицы ниже
и не проверка переданного `--binary`. Полный сохранённый эталонный набор находится
в `scripts/benchmark_klite_reference.py` и запускается явным флагом:

```
python3 scripts/fetch_klite_samples.py --benchmark-reference --auto   # пинные референс-сэмплы -> benchmarks/data/klite
python3 scripts/fetch_klite_pack_components.py   # состав пака по изданиям -> benchmarks/klite-pack-components.json
python3 scripts/validate_klite_coverage.py --benchmark-reference --binary target-media/release/fvid
```

1. Фикстура генерируется локальным FFmpeg-энкодером (5 видеокадров / 0.2 с аудио).
2. Для кодека, которого в локальном энкодере нет, берётся закреплённый по sha256
   референс-сэмпл. Источник по умолчанию — FATE-зеркало FFmpeg, и `--auto` подбирает файл сам:
   по имени декодера из каталога-кандидата берётся самый маленький образец, который `ffprobe`
   называет нужным кодекс. Чего в FATE нет, пинится по абсолютному URL (`SAMPLES` в том же
   скрипте), а что в FATE лежит только в намеренно испорченном виде — ищется в архиве образцов
   FFmpeg (`EXTERNAL`, индекс `allsamples.txt`). Кандидат принимается, если `ffprobe` назвал
   нужный кодек, а для видео — ещё и когда `ffmpeg -xerror` дочитал поток до конца без ошибок:
   иначе строка проверяла бы обработку повреждений, а не декодирование. Для аудио целость
   контейнера не требуется (этот путь переживает битый вход намеренно), но из файла хоть что-то
   должно читаться: кандидат отбирается числом кадров, которое из него вытаскивает CLI. Локальный файл подключается через
   `scripts/fetch_klite_samples.py --benchmark-reference --add ROW URL_или_ЛОКАЛЬНЫЙ_ПУТЬ`. Расхождение хэша роняет
   гейт, поэтому подмена образца замечается сразу. Бюджет фикстуры — 8 МБ; для `mtv`, `dav` и
   `dsd` сделано исключение (`BUDGETS`), потому что иначе их ни переупаковать, ни обрезать, а
   `icod` и `nclc` закреплены первыми пятью кадрами больших эталонов (`CUTS`). Если цель строки —
   «эта сборка файл не читает», ожидаемый отказ задаётся пустым именем кодека в списке
   принимаемых: пин ставится, а `absent-in-build` фиксируется по фактической прочитке.
3. Видео: `fvid media decode` обязан вернуть то же число кадров, что `ffprobe -count_frames`.
   Аудио: `fvid media decode-audio` обязан вернуть PCM, совпадающий с FFmpeg-оракулом
   побитово по каждому каналу (целочисленный хэш потока не сравним: fvid пишет WAV без
   channel layout, и многоканальный файл расходится из-за переупорядочивания каналов).
4. Отдельно пинется разделение строгости входа: `remux` закрепленного повреждённого сэмпла
   обязан отвергнуть пакет с `AV_PKT_FLAG_CORRUPT` и не опубликовать выход (`copy_strictness:
   rejected`), тогда как `decode-audio` того же файла обязан декодировать всё читаемое.
5. Статусов у строки пять. `covered` — доказано; `needs-sample` — образца нет;
   `absent-in-build` — декодера (или демуксера) нет в собранном FFmpeg, и K-Lite тянет такой
   формат собственным фильтром, так что сравнивать не с чем; `no-fixture` — сломался маршрут
   локальной фикстуры; `fails`/`container-gap`/`missing` — пробел fvid. Последние четыре
   (кроме `needs-sample` и `absent-in-build`) роняют гейт.
6. Раздел «Матрица» ниже перегенерируется из тех же чисел:
   `python3 scripts/validate_klite_coverage.py --benchmark-reference --markdown docs/KLITE_COVERAGE.md`.
7. Итог — `benchmarks/klite-coverage.json`; скрипт выходит с кодом 1 при любой строке
   `fails`/`container-gap`/`missing`/`no-fixture`, при `copy_strictness: leaked`, при строке
   таблицы возможностей K-Lite, которой нет в матрице (`ability.uncovered`), и при строке,
   списанной с `absent-in-build`, которую сборка на самом деле раскодировывает
   (`decoder_mapping`), при строке, помеченной собственным декодером, но не прогнанной через
   собственный пайплайн (`native-column`), при колонке «Через MCP», не совпадающей с политикой
   контейнеров (`mcp-policy`), при компоненте пака, которому нечем ответить (`pack-components`), при
   декодироваемом сборке изображенческом кодексе без строки матрицы и без честной отписки
   (`image-codec-rows`), и при строке, которая потерялась по дороге в матрицу (`row-accounting`).
   Запись прогона совпадает сама с собой: два подряд пуска дают тот же файл байт в байт, потому
   что локальная фикстура названа своим именем под меткой `<run-tmp>/` вместо случайного каталога
   пуска, а байты видеофикстуры не пинятся — многопоточный энкодер пишет их дважды по-разному, и
   хэш такой фикстуры опровергался бы следующим же прогоном. Хэш остаётся доказательством там,
   где файл определяется своим описанием, а не удачей пуска: у внешнего образца пин сверяется
   перед прогоном, у строки изображения байты фикстуры за прогоны не менялись.
8. Состав списка проверяется машиной, а не вниманием: `benchmarks/klite-ability.json` — 194<!--ability_lines:строка:строки:строк--> строки
   официальной таблицы возможностей, `ability_gaps()` в гейте ищет для каждой строку матрицы по
   FourCC/AudioTag, расширению файла, имени кодека или семейному соответствие (`ABILITY_FAMILY`).
   Первая же проверка нашла пять форматов, которые матрица молча не покрывала: Creative YUV,
   Zip Motion Blocks, Autodesk RLE, CorePNG и Gryphon's Anim Compressor. Сейчас `uncovered` пуст,
   и удалить строку из списка, оставив позицию K-Lite незакрытой, больше нельзя.
9. `absent-in-build` сам по себе себе не довод: статус не роняет гейт, поэтому неверный маппинг
   строки на дескриптор просто выкидывает позицию из доказательства. Проверка та же, что и с
   составом списка — подпись строки из таблицы вендора ищется в описаниях декодируемых кодексов
   `ffmpeg -codecs`, и совпадение даёт регрессию `decoder-mapping` (так и нашёлся `i263` → `h263i`).
   У того же статуса есть и вторая половина: он утверждает, что сборка ничего не может, — значит
   у каждой такой строки должно быть названо, какого компонента не хватает и чем K-Lite закрывает
   формат. Причины лежат в `ABSENT_REASON` и печатаются прямо в строке матрицы, а замер дополнен
   конфигурацией самой библиотеки (`ffmpeg -buildconf`): строка без причины, причина у строки,
   которая снова доказана, и любой `--disable-` в сборке дают регрессию `absent-reasons`.
10. Колонка «свой декодер» тоже измеряется, а не переписывается от руки: гейт гоняет аудио-строки
   через `examples/audio_probe`, который вызывает `fvid::codec::make_audio_decoder` напрямую, без
   libavcodec, и требует, чтобы собственный путь раскодировал все пакеты, назвал тот же кодек, что
   и строка, и отдал то же число сэмплов на lossless-фикстуре. Видео-строки гоняются так же:
   `examples/decode_native_rgb` ведёт `NativeReader` без окна и сверяет число кадров с ffprobe на
   этом же файле (см. «Границы native-пути»). Расхождение — регрессия
   `native-column`. Проверка сразу показала, что руками поддержанный список недосообщал четыре
   строки (`mp3`, `flac`, `pcm`, `pcm_qt`), и поймала поломку фикстуры: нативный энкодер Vorbis,
   как и `s302m`, читает `-strict -2` только как опцию вывода.
11. Измеряется и вторая поверхность продукта: те же два примера прогоняются по файлу каждой строки
    и дают колонку «В плеере» — открывает ли собственный конвейер fvid именно этот файл, без
    libavcodec. Колонка информационная (расширять плеер — продуктовое решение, а не вопрос
    доказательства), но причины отказов считаются по тексту самого конвейера, и всё, что не
    распознано, копится в отдельном числе `unclassified` — переименованное сообщение видно как
    сдвиг числа, а не как устаревшее предложение в тексте. Запись RGB-выхода ограничена
    `RLIMIT_FSIZE`, иначе строка, которую native-путь принимает целиком, выписывает гигабайты.
12. Третья поверхность — MCP — измеряется тем же прогоном и даёт колонку «Через MCP»
    (`measure_mcp()`). Сервер поднимается `fvid mcp --root <корень> --stdio`, одним экземпляром на
    корень (репозиторий и временная папка фикстур), чтобы ради чтения не переносился ни один байт;
    зовётся только `fvid_probe`. Ответ сверяется с `fvid media probe` на том же файле и со
    списком `format_whitelist`, вычитанным из исходника: расхождение в любую сторону — регрессия
    `mcp-policy`. Колонка не роняет гейт сама по себе (расширять поверхность — продуктовое
    решение), но врать уже не может.
13. Таблица возможностей — не весь пак. Его состав по изданиям пересобирается машиной:
    `python3 scripts/fetch_klite_pack_components.py` читает `klcp_contents_comparison.htm` (сетка
    «есть/нет/частично» по Basic/Standard/Full/Mega) и `download_kl.htm` (маркетинговые пункты,
    которые нигде в таблице не перечислены) и пишет `benchmarks/klite-pack-components.json` — 32<!--pack_components-->
    компонента. Генератор не даёт пересказу уехать от источника: пункт-исключение засчитывается
    только дословным совпадением формулировки со страницей вендора (так и отвалился
    «DVD and Blu-ray playback», у вендора — «DVD and Blu-ray (after decryption)»). Гейт требует,
    чтобы каждый компонент был отражён в `COMPONENT_MAP`: либо строками матрицы (или целым её
    разделом — и тогда все строки раздела обязаны оставаться доказанными, а не просто
    присутствовать), либо явным «это не раскодирование» со ссылкой на файл, который действительно
    лежит в дереве. Невнятный компонент, пропавшая строка, битая citation, отписка, пережившая
    исчезновение компонента, и сетка издания с потерянной колонкой — всё это регрессия
    `pack-components`. Именно эта проверка заставила доказать содержимое Mega-компонента
    «image formats» отдельными строками, а не одной фразой в тексте.
14. Изображения — отдельная ось матрицы (36<!--image_rows:строка:строки:строк--> строк, раздел «Изображения»). Их набор выводится из
    самой сборки: `image_codecs()` берёт из `ffmpeg -codecs` те декодируемые кодексы, которые FFmpeg
    сам описывает словами image/bitmap/raster, плюс `webp` (его называет таблица возможностей). Так
    список не зависит от догадки про расширения, которых вендор не публиковал ни для одной редакции.
    Фикстура — одиночный кадр, записанный форматом в своё расширение (`apng` пятью кадрами, иначе
    файл был бы обычным PNG), а если ни энкодера, ни образца нет — байты, которые скрипт пишет сам
    по спецификации контейнера: так закрылись `xpm`, `gem` и `jv`. Рукописная фикстура проходит ровно
    тот же бар, что и внешний образец: `ffmpeg -xerror` обязан прочесть её без ошибок, иначе она
    доказывала бы обработку повреждений, а не декодирование. Исключение одно, и оно измерено: у
    формата, чей справочный демуксер кончает целый поток ошибкой вместо конца (`TOLERATED_EOF`),
    планка `-xerror` не снята, а заменена замером — без неё справочное чтение обязано взять все
    объявленные кадры и выйти нулевым кодом, строгий `-count_frames` обязан насчитать столько же, а
    `fvid media decode` — отдать кадр и назвать ненулевое число пропущенных чтений. Строка
    засчитывается только если фикстура пробуется тем
    же дескриптором, который она называет, иначе это доказательство другой строки. Если сигнатуры у
    байтов нет вовсе, формат закрывается указанием демуксера на входе: `gem` доказан так
    (`--input-format gem_pipe`), и меряются обе половины — чтение с именем обязано дать кадр, чтение без
    имени обязано отказать, иначе указание оказалось бы удобством харнеса, а не требованием формата.
    Форматов без строки осталось два (`vc1image`, `wmv3image`), оба лежат в `IMAGE_UNPROVABLE`, а
    реестр рукописных исключений `UNREACHABLE` пуст: его последние кандидаты стали строками матрицы —
    `gem` из-за входа, а не декодера, `jv` из-за терпимости, а не материала. Причину у
    каждой строки пишёт прогон, а не память: у оставшихся двух отписок замеряются все три опоры
    причины — энкодер сборки, индекс архива образцов и дескриптор, которым пробуется VC-1-поток
    матрицы. И отписка самоуничтожается: если
    сборка обзаведётся энкодером, появится закреплённый образец, скрипт научится писать такой файл сам,
    замер увидит, что fvid добирается до дескриптора по одному лишь расширению, — гейт потребует строку.
    Расхождение — регрессия
    `image-codec-rows`.
15. Матрица не теряет строк по дороге: `row_accounting()` сверяет число измеренных строк каждого
    раздела с числом, записанным в самих списках `VIDEO`/`AUDIO`/`CONTAINERS`/`IMAGE`, и ловит
    дубликаты. Это не перестраховка — прогон, на котором вставка image-цикла съела `rows.append` у
    цикла контейнеров, потерял 26 строк, и ни одна предыдущая проверка на этом не споткнулась:
    пропавшая строка просто перестаёт о себе спрашивать, а сигнал пришёл сбоку, через
    `vendor-ability-lines`: из 45 контейнерных строк в матрице доехало 17.

## Как отобраны строки

Строка матрицы — позиция из официальной таблицы возможностей K-Lite 20.0.0
(`klcp_ability_comparison.htm` на codecguide.com: контейнеры, видео- и аудиоформаты с
FourCC/AudioTag), сведённая к декодерам: одна строка на тот кодек libavcodec, на который
LAV/ffdshow реально диспетчеризуют вызов. Группы FourCC, попадающие в один декодер, остаются
одной строкой (`XVID/DX50/MP4V…` → `mpeg4`, но `MP42`/`MP43` — отдельные, потому что это
другие декодеры; `DVSD…DVHP` → `dvvideo`; DTS, DTS-ES, DTS-HD MA/HRA, LBR → `dca`). Кроме
кодеков в матрицу входят контейнеры, которые регистрирует Icaros, и VFW/ACM-набор установщика
(x264vfw, Xvid, Lagarith, Huffyuv, AC3ACM, LAME).

Таблица возможностей — не весь пак, и вторая половина строк берётся оттуда, где это видно: из
списка компонентов по изданиям (`benchmarks/klite-pack-components.json`). От него в матрицу
попали 36<!--image_rows:строка:строки:строк--> строк изображений — Mega-компонент «MPC Image Source», для которого вендор не
публиковал ни одной строки таблицы, — и строка `h264mvc`: плагин 3-D декодирования, который
Full/Standard поставляют отдельно и который в этой сборке FFmpeg отсутствует как класс. Остальные
компоненты пака (рендереры, фильтры пост-обработки, обёртки проводника, Codec Tweak Tool) — не
раскодирование; каждому из них `COMPONENT_MAP` отвечает либо ссылкой на уже замеренную
поверхность, либо явным сказуемым с файлом, где это видно.

Так получается 143<!--codec_rows--> строки кодеков плюс 45<!--container_rows--> контейнерных плюс 36<!--image_rows:строка:строки:строк--> строк изображений (224<!--rows_total:строка:строки:строк--> строки) —
против **499<!--decodable_codecs-->** кодексов,
которые fvid умеет раскодировать просто потому, что они собраны в линкованном FFmpeg
(`inventory.decodable_codecs` в `benchmarks/klite-coverage.json`). Своего списка разрешённых
кодеков `fvid-media` не держит (whitelist включается только в standalone-режиме), то есть
наследует их все. Матрица потому и доказывает выборочно: продуктовые позиции K-Lite проверяются
поштучно, остальное — свойство линковки, а не работа.

Гейт числит и обратную сторону: из каких строк матрицы декодера в сборке нет. Это статус
`absent-in-build` — для K-Lite такие форматы обслуживают собственные фильтры (OptimFROG,
AC-4, плагин H.264 MVC), и доказывать паритет с libavcodec по ним нечем. Две строки когда-то попали в этот
статус ошибочно — MPEG-4 ALS (декодер `als` стоит за дескриптором `mp4als`) и Intel H.263
(`h263i` за FourCC `i263`), и теперь такие подмены ловит проверка ниже. У
контейнеров та же проверка идёт по имени демуксера в `ffmpeg -formats`, а когда образец всё-таки
есть — по факту прочитки: закреплённый `.mid` не открывает даже `ffprobe`, так что MIDI, CD-DA и
трекер-модулы попадают в `absent-in-build` замером, а не по документации. `h264mvc` — из той же
операции: строка обязана называть дескриптор, которого `ffmpeg -codecs` действительно не выдаёт,
и поэтому это запись замера, а не пересказ FAQ вендора. Отдельная строка
инвентаря — `matrix_codec_rows`, чтобы список строк нельзя было тихо сократить, а `row_accounting`
сверяет уже измеренное с самими списками строк.

Граница измерения тоже стоит в одном месте. Матрица проверяет `fvid media decode` и
`fvid media decode-audio` — они наследуют весь набор декодеров собранного FFmpeg.
MCP-обёртка тех же вызовов (`src/mcp/mod.rs`) дополнительно ограничивает *контейнеры*:
`with_standalone_inputs` передаёт libavformat `format_whitelist`, в котором playlist- и
manifest-демуксеры исключены, чтобы вход не тянул за собой чужие файлы. Список этот живёт в
`crates/fvid-media/src/lib.rs`, гейт вычитывает его оттуда и печатает в сгенерированном разделе,
поэтому переписывать его прозой здесь не нужно — он не разъедется с кодом.

Что именно этот список отсекает — тоже замер, а не описание: `measure_mcp()` поднимает
`fvid mcp --stdio` (одним сервером на корень, чтобы ничего не копировать ради чтения) и зовёт
`fvid_probe` на файле каждой строки, а тот же файл отдельно пробуется `fvid media probe` без
политики. Из 224<!--rows_total:строки:строк:строк--> строк сервер открывает **133<!--mcp_yes-->**, отказывает 85<!--mcp_no-->, 6<!--mcp_not_run--> не мерялись
(`absent-in-build`). Отказ засчитывается только тогда, когда демуксер файла вправду вне
allowlist-а: и «открыть запрещённое», и «запретить названное» роняют гейт как `mcp-policy`, так что
колонка не может тихо перестать соответствовать политике. В этом прогоне в отказе 50<!--mcp_no_non_image:строка:строки:строк--> строк —
RealMedia (`.rm` вместе с rv10/rv20/rv40/realvideo и аудио-ветками cook/sipr/ralf/ra_144), MXF, DV,
AIFF, CAF, au, SWF, WTV, IVF, MTV, DHAV, PVA, сырые элементарные потоки (vc1, dirac, vvc, ac3,
eac3, dts, amr) и обёртки lossless-аудио (tta, wv, ape, mpc8, tak, shn, aea, oma, act, dsf, dss), плюс
легаси-игровые контейнеры bink/smk/flic/psxstr. К этому же списку добавились 35<!--image_mcp_no--> из 36<!--image_rows:строки:строк:строк--> строк
изображений: из still-демуксеров политика называет только `png_pipe` и `jpeg_pipe`, а JPEG-строка в
матрице живёт в разделе видео (`mjpeg` в контейнере), так что от всего раздела через сервер проходит
одна `.png`. Это решение про границы вызова, а не пробел
раскодирования: матрица по-прежнему отвечает на вопрос «можно ли это раскодовать», и ни одна
отказанная MCP строка не перестаёт быть покрытой.

Там же стоит и граница проигрывания, потому что матрица измеряет раскодирование, а K-Lite
обещает «ваш проигрыватель это откроет». Из 218<!--rows_covered--> доказанных строк в окно попадают пять — `aac`,
`pcm_qt`, `y4m`, `m4a`, `mka`. Это уже не вывод по коду dispatch-а, а прогон: `measure_surfaces`
ведёт файл каждой строки через `examples/decode_native_rgb` и `examples/audio_probe`, то есть через
тот же выбор читателя, что делает `fvid play`. `fvid media play` (`src/media_cli.rs` →
`fvid_media::play_paths`) открывает вход без ограничения по формату, то есть наследует тот же набор,
что и `decode`. Собственный же плеер знает три семейства контейнеров — Y4M, EBML (`.webm`/`.mkv`) и
ISO-BMFF (`.mp4`/`.mov`) — плюс сигнатуры PNG, GIF и JPEG, которые распознаёт, но тут же и
отбраковывает: у неподвижной картинки нет таймлайна, и `NativeReader` отвечает на это
«still-image playback is not supported». Запасного маршрута через FFmpeg у него нет. Значит `.avi`,
`.asf`, `.rm`, `.wtv`, `.flv` и `.ts` из матрицы — это путь `fvid media play`, а не `fvid play`; в
MCP команды проигрывания нет вовсе.

Разбивка отказов по причинам печатается из этого же прогона (`player_surface.causes`) и вручную не
переписывается, и непонятной корзины в ней больше нет: строки изображений делятся ровно так, как
замерено, — 32<!--image_player_signature--> из 36<!--image_rows--> не распознаются по сигнатуре, а 4<!--image_player_still--> (`apng`, `gif`, `jpegls`, `png`) доходят до
ветки картинок и отбраковываются как неподвижные. По остальным осям разбивка по типам
(`player_surface.by_kind`) тоже в матрице своя: из доказанных видео-строк плеер не несёт ни одной,
и после image-оси очередь работ у плеера длиннее на 36<!--image_rows:строка:строки:строк--> строк.

## Повреждённый вход: что теперь терпится

K-Lite существует потому, что бытовая библиотека файлов побита: усечённые хвосты, кривые
заголовки, пакеты с флагом corrupt. FFmpeg CLI на таких файлах добирает сколько может и выходит
с кодом 0; fvid раньше обрывал декод на первой ошибке. Сейчас аудио-путь `fvid media decode-audio`:

- пропускает пакет, который декодер отверг как `AVERROR_INVALID_DATA`, и продолжает поток;
- принимает пакеты с `AV_PKT_FLAG_CORRUPT` — решение остаётся за декодером;
- отчитывается полем `decode_errors` в `fvid media decode-audio` (в него сложены и отвергнутые
  декодером пакеты, и повреждённые чтения demux), так что терпимость видна в
  выходе, а не спрятана; больше 64 повреждённых чтений demux останавливают чтение — счётчик
  суммарный по всему потоку, а не «подряд»;
  остановка не выбрасывает уже декодированное: поток дозаполняется до конца буфера декодера,
  `sample_frames` остаются честными, а ошибкой падает только вход, из которого не удалось
  вытащить ничего. Раньше guard обрывал прогон с ошибкой и терял весь PCM; пинит это строка
  `g729`, где `.act`-демуксер отдаёт 13 158 кадров и спотыкается только на хвосте (65 ошибок),
  а сравнение с FFmpeg-оракулом на том же файле совпадает побитово;
- вторым таким пином стала строка `pva`: 1-мегабайтный FATE-обрезок, который `.pva`-демуксер
  бросает с `invalid syncword`, отдаёт те же сэмплы на канал, что и CLI, при `decode_errors` 65 —
  то есть guard срабатывает и на повреждении контейнера, не теряя декодированное.

`remux`/`trim`/`concat` и остальные copy-пути строги по-прежнему: битые байты не должны
попадать в новый файл. Проверяется это пунктом 4 гейта.

Видео-ветка (`fvid media decode`) получила ровно ту поблажку, о которой просил один формат: чтение
пакета, которое демуксер отдаёт как `AVERROR_INVALID_DATA`, пропускается и считается в поле
`decode_errors` (суммарно по всему потоку, как и в аудио), больше 64 таких чтений обрывают чтение, но
декодер при этом всё равно опоражнивается, и
`video_frames` остаётся тем, что поток действительно отдал. Ошибкой падает только вход, не отдавший
ни одного кадра. Пакеты, которые отверг сам декодер, по-прежнему строги: терпим здесь только конец
потока, а не середина.

Замеренная причина — JV: его демуксер заканчивает **целый, записанный по спецификации** файл кодом
`AVERROR_INVALIDDATA` вместо конца, то есть справочная реализация прощает себе такую концовку, а
строгий путь fvid — нет. Прежняя сборка на тех же байтах отвечала `read packet: Invalid data found
when processing input (-1094995529)` и не давала ничего; теперешняя отдаёт кадр и `decode_errors: 65`,
и этой строкой (`jv`) закрыт последний изображенческий формат, чей отказ касался терпимости, а не
материала. Планка `-xerror` для таких строк не отброшена, а заменена замером: без `-xerror`
справочное чтение обязано взять все объявленные кадры и выйти с нулевым кодом, `ffprobe -count_frames`
обязан насчитать столько же, а `decode_errors` обязан быть больше нуля — иначе строка не засчитывается.
Как только `ffmpeg -xerror` снова пройдёт, гейт покраснеет: фикстура такого формата станет
`no-fixture` с требованием убрать поблажку из `TOLERATED_EOF`, а имя, оставленное в этом множестве
без строки, ловит регрессия `image-codec-rows`. Проверяют это два теста в `crates/fvid-media`: целый
файл сохраняет кадр при ненулевом счётчике, а поток, не отдавший ни кадра, остаётся ошибкой.

Асимметрия сузилась, но не исчезла: аудио-путь переживает битый вход целиком (битые пакеты, флаг
corrupt, оборванный контейнер), видео-путь — только его конец.

## Что осталось и почему

Из 224<!--rows_total:строки:строк:строк--> строк 218<!--rows_covered--> доказана, ни одна не падает, и строк «ждём образца» не осталось. Шесть
оставшихся ограничены не настройкой сборки и не раскодированием: этих компонентов нет в FFmpeg.
Двум из них на помощь пришёл собственный код fvid, и об этом сказано отдельно ниже.

**Декодера или демуксера нет ни в сборке, ни в upstream** (`absent-in-build`). Сборка, к
которой прилинкован fvid, — homebrew-ый FFmpeg 9.0.2, и в её `ffmpeg -buildconf` 0<!--ffmpeg_disable_flags-->
отключающих флагов, так что «надо было включить флаг» как объяснение исключено измерением. Все
6<!--rows_absent--> таких строк имеют измеренную причину (`rows_absent_explained` = 6<!--rows_absent_explained-->), и печатает её сама
строка матрицы; строка без причины, причина у строки, которая снова доказана, и появление в
конфигурации сборки `--disable-` — всё это регрессия `absent-reasons`.

Кодеки — `optimfrog`, `ac4`, `h264mvc`: их нет ни в `ffmpeg -decoders` этой сборки, ни в
документированном списке компонентов
[`ffmpeg-codecs.html`](https://ffmpeg.org/ffmpeg-codecs.html), где OptimFROG, H.264 MVC и
AC-4 не названы вовсе. K-Lite обслуживает их собственными фильтрами (для H.264 MVC это отдельный
плагин в Standard/Full), сравнивать с libavcodec нечем ни при какой конфигурации, а по `optimfrog`
принята явная отказка. Измеряется при этом, какой именно половины не хватает: у `h264mvc` (`.mov`) и `ac4` (`.mp4`, и отдельно — сырой `DE ac4 raw AC-4` в `ffmpeg -formats`)
контейнер этой сборки читается, то есть не хватает только декодера, а у `optimfrog` нет и демуксера
`.ofr`. Контейнерные строки — `midi`, `cda` (CD-DA) и модули `it/xm/s3m/mod`: их K-Lite закрывает не
LAV, а Bass Audio Source; в `ffmpeg -formats` этой тройки нет, как нет её в списке форматов
FFmpeg [`ffmpeg-formats.html`](https://ffmpeg.org/ffmpeg-formats.html), а закреплённый `breeze.mid`
не открывает даже `ffprobe`. Из тройки `cda` остаётся единственной, кому не хватает и внешнего
демуксера, и закреплённого файла; её так и ищут —
`python3 scripts/fetch_klite_samples.py --benchmark-reference --add ROW ПУТЬ_или_URL`.

**Ещё 2<!--rows_own_pipeline:строка:строки:строк--> строки из этих шести доказаны своим кодом, а
не FFmpeg.**
По `midi` сравнивать было нечем, поэтому читатель и синтезатор написаны здесь:
`src/container/smf.rs` разбирает Standard MIDI File (треки, темповую карту, running status) и режет
его на окна по 100 мс, `src/codec/midi_decoder.rs` превращает эти окна в звук, `src/playback_smf.rs`
отдаёт их плееру как `AudioStream`. Доказательство снимает прогон, а не текст:
`measure_own_pipeline()` гонит свой конвейер и на фикстуре, написанной здесь по спецификации SMF, и
на закреплённом внешнем `breeze.mid` (сверенном по sha256), требует раскода всех окон, сверяет
число кадров с длиной, которую заявляют их собственные штампы, и читает обратно сам PCM — молчание
строку не доказывает. Фикстура `.xm` написана тем же кодом, который её читает, поэтому её байты
тоже закреплены по sha256: правка, устроившая обе стороны сразу, иначе прошла бы как успех.
Внешнего take'а у неё нет, и это не воспоминание о поиске, а замер прогона: он перебирает индекс
`samples.ffmpeg.org` по расширениям `.xm`/`.s3m`/`.it` и по названиям модульных архивов и требует,
чтобы кандидатов было ноль (`own_take_search`); появится хоть один — гейт скажет, что строка
осталась ему должна.
По `tracker` то же самое для модулей FastTracker II: `src/container/xm.rs` читает `.xm`
(инструменты, сэмплы, колонку темпа) и раскладывает таймлайн в пакеты по одному ряду на пакет,
`src/codec/xm_decoder.rs` микширует ряд, `src/playback_xm.rs` отдаёт его плееру как `AudioStream`.
Профиль микшера — ноты, лупы, громкость канала и панорама; конвертов и колонки эффектов он не
играет, и это не тихая дыра. Без volume-конверта ноту после key-off держать нечем, поэтому key-off
её обрывает — ровно как в libxm и в самом FastTracker II, — а всё остальное, что ряд просит и не
получает, считает `Ignored` и показывает тест.

Точные числа печатает строка матрицы. Отказ `ffprobe` на каждом из файлов та же проверка измеряет
заново, так что «FFmpeg научился читать `.mid`» сам погасит эту строку и потребует обычное
доказательство. Статус при этом остаётся `absent-in-build`: покрытой матрица называет
раскодирование через `fvid media`, а за ним по-прежнему нечего.

**Два изображенческих формата без строки.** Обоим (`vc1image`, `wmv3image`) не хватает материала, и с
этого прогона за это отвечают три замера, а не одно воспоминание
(`image_surface.unprovable_evidence`). Энкодера формата у сборки нет — это `ffmpeg -encoders`. В
собственном индексе архива образцов (`samples.ffmpeg.org`, кэш `benchmarks/data/klite/.allsamples.txt`)
нет ни одного пути, названного этим дескриптором либо расширением семейства HD Photo (`.jxr`,
`.wdp`, `.hdp`, `.hdl`, `.emv`): 0<!--image_unprovable_candidates--> совпадений, и нуль честен ровно
пока индекс прочитан — без кэша сама отписка становится регрессией, потому что «материала нет» без
поиска есть утверждение, а не замер. Третий вопрос задаётся тому VC-1-потоку, который у матрицы уже
есть: закреплённый take пробуется как `vc1`, и значение берётся из замера строки, а не из текста
отписки; ответь он `vc1image`, строку пришлось бы писать. Индекс FATE этой мерой не покрыт — `--auto`
перебирает его построчно там, где строка просит образец, так что «материала нет» здесь сказано про
архив образцов, а не про все репозитории FFmpeg. Ни одна из причин не держится на памяти: все
2<!--image_unprovable_measured:причина:причины:причин--> причины подтверждены этим же прогоном.
Третий кандидат в эту отписку, `jv`, из неё вышел по другой половине: материала хватает, файл гейт
пишет сам по спецификации, а мешал конец потока — решал это decode-путь, а не архив образцов
(см. «Повреждённый вход» выше).

`gem` ушёл так же честно и по другой половине: у потока нет ни сигнатуры, ни
зарегистрированного расширения, и справочно он читается, только если демуксер назвать
(`-f gem_pipe`). `fvid media probe` и `decode` принимают теперь то же указание (`--input-format`),
`avformat_open_input` вызывается с ним вместо нулевого `AVInputFormat`, и строка доказана обеими
половинами: с именем фикстура отдаёт кадр, без имени обязана быть отвергнута. Вторая половина — не
формальность: читался бы файл без названия, и указание оказалось бы удобством харнеса, а не
требованием формата; гейт так и пишет (`so the hint is not a requirement`). Указание демуксера
обходит пробу, а вместе с ней и белый список контейнеров, поэтому под политикой автономного входа оно
отвергается — это стоит отдельным тестом в `crates/fvid-media`, и оттуда же «нет» в колонке «Через
MCP» у строки `gem`.

`jv` — строка матрицы с тех пор, как видео-путь читает конец потока, который его демуксер отдаёт
ошибкой (правило и замер до/после — в «Повреждённый вход»). Он пробуется сам (`codec_name=jv`),
один кадр фикстуры раскодируется, и планка `-xerror` не проходила не файлом, а справочной
реализацией. Заменена она не отпиской, а замером: без `-xerror` справочное чтение обязано взять все
объявленные кадры и выйти нулевым кодом, строгий `ffprobe -count_frames` — насчитать столько же, а
`decode_errors` — быть больше нуля. Если `-xerror` когда-нибудь пройдёт, гейт покраснеет и потребует
убрать поблажку (`image-codec-rows`).

Реестр таких рукописных исключений (`UNREACHABLE` → `image_surface.unreachable`) сейчас пуст ровно
по этой причине: его оба кандидата стали строками. Заодно измерением была проверена прежняя
формулировка про `gem` («ни энкодера, ни take-а в архиве»): совпадения в индексе архива и правда
посторонние (netgem-исходники и `haegemonia.avi`), каталога формата в FATE нет — но решала строку не
удача с образцом, а указание формата на входе.

Про `pgmyuv` ровно та же отписка оказалась неверной, и нашёл её не человек, а гейт. Формат
действительно не имеет сигнатуры — заголовок у него обычный PGM, — поэтому в матрице он сидел как
«без названия демуксера проба отдаёт `pgm`». Но `fvid media decode` читает файл не только по пробе:
libavformat добирается до демуксера и по расширению, а `.pgmyuv` у него зарегистрировано. Записанная
тем же маршрутом фикстура вернула `codec_name=pgmyuv`, `64x48`, `yuv420p`, чистое чтение прошла без
`-f`, и `fvid media decode` насчитал в ней один кадр — то есть строка доказывала ровно тот декодер,
который называет, и она в матрице есть. Смысл этого эпизода не в одном формате: отписка про
«сигнатуры нет» без проверки маршрута по расширению не является замером, поэтому рукописная фикстура
спрашивается у fvid в том же прогоне, который её же и записал, и при успехе отписка объявляется
устаревшей.

Отписка в `IMAGE_UNPROVABLE` живёт ровно пока невыполнимо условие, при котором она была написана:
гейт требует строку, как только у сборки появится энкодер формата, где-то закрепится целый образец,
скрипт научится писать такой файл по спецификации — или замер увидит, что вход добирается до
дескриптора без образца. Именно так из этого списка ушла `xpm`: текст XPM скрипт записал сам, и
reference-реализация читает его чисто. Так же ушли `gem` (как только `media probe/decode` стали
принимать имя демуксера) и `jv` (как только видео-путь прочитал концовку своего демуксера) — отписки
переставали быть правдой в том же прогоне, где появлялся код. Очередь у оставшихся одна: `vc1image` и
`wmv3image` ждут образец, который пробовался бы своим дескриптором, а не `vc1`, — и очередь
перечисляет тот же замер: путь в индексе архива под расширением HD Photo, энкодер формата или
VC-1-строка, пробовавшаяся image-дескриптором, превращают отписку в регрессию
`image-codec-rows`.

## Четыре строки, закрытые в этом же замере после «недоказуемо»

Способ здесь важнее результата, потому что три из четырёх отказов были ошибкой метода, а не
отсутствием образца.

`i263` вообще не должен был числиться отсутствующим: сборка раскодирует Intel H.263 дескриптором
`h263i`, а строка искалась по имени `i263` — по FourCC из таблицы K-Lite. Ошибка была тихой,
потому что `absent-in-build` не роняет гейт. Теперь это проверяется машинно: для каждой строки без
декодера её подпись из таблицы вендора ищется в описаниях декодируемых кодексов
`ffmpeg -codecs`, и совпадение (`"Intel H.263"` → `h263i`) даёт регрессию `decoder-mapping`. На этом
замере гейт так и поймал себя на первом же кандидате, а после правки маппинга список
пуст — `ac4` и `optimfrog` описаний в сборке не имеют, а `geov` дескриптор имеет и с ним доказан ниже.

`i263` и `arbc` закрыты настоящими образцами из `V-codecs/I263/` (340 КБ, `i263.avi`) и
`V-codecs/ARBC/` (3.8 МБ, `ED.AVI`) — архив образцов держит каталоги по FourCC, и оба проходят
чистую прочитку `ffmpeg -xerror`. Прошлый вывод «потоков нет, лежат только драйверы» получился из
`grep … | head`: совпадения в `allsamples.txt` были, а вывод обрезался до них. Проверка на
«образца нет» теперь делается без усечения.

`geov` был записан как «декодера нет», а за ним оказались два штатных дескриптора: GeoVision
метит своим FourCC то, что кодирует обычный движок. `V-codecs/GAVC/GeoVision_camera.avi` — это
`GAVC / H.264 (High)`, 1920×1080, и `fvid media decode` отдаёт по нему 190 кадров при
`decode_errors = 0`, ровно столько же, сколько насчитывает `-count_frames` у того же libavcodec;
строка доказана этим взятием и закреплена по sha256. Второе, более старое взятие того же
вендора — `V-codecs/geov.avi`, `GEOV / mpeg4`, 720×240: заголовок его кадров помечен повреждённым
и у самой ссылки (`header damaged`, `-count_frames` видит 9 из объявленных 91), а видеопуть fvid
на таком пакете останавливается. Это не «декодера нет», а вопрос терпимости к битому заголовку;
он остаётся отдельной проверкой и сам по себе числу покрытых строк не служит.

`pva` доказывается по аудиопотоку, и это оговорено честно: целых PVA-взятия нет ни в FATE, ни
в архиве образцов (везде `Invalid data` от самого демуксера), а претензия строки — что fvid
распакует `.pva` и декодирует то, что внутри. FATE-обрезок в 1 МБ отдаёт 84 MP2-кадра, fvid
выдаёт по ним побитово совпадающий PCM и останавливается на 65-й подряд ошибке демуксера ровно
там, где и CLI; `decode_errors` при этом публикуется. Видеопуть PVA этим не доказан — он доказан
строкой `mpeg2`, но сам видео-путь с тех пор переживает повреждённый конец потока так же, как
аудио-путь (см. «Повреждённый вход» выше), и строги в нём остались середины потока и copy-операции.

`s302m` оказалась недоказуемой из-за выбора обёртки, а не отсутствия упаковщика: WAV, QuickTime и
NUT тег отказываются писать, MXF требует видеодорожку и падает на `pcm_rechunk`, но MPEG-TS — это
ровно та обёртка, в которую ST 302M кладёт суть, и `-f mpegts -c:a s302m` пишется и читается
чисто. Первая попытка всё равно упёрлась в `-strict -2`: энкодер принимает его только как опцию
выхода, а не как глобальную.

Три позиции закрыты ценой исключения из бюджета фикстуры: обычно пин не превышает 8 МБ, а
`mtv` (19.8 МБ), `dav` (25.8 МБ) и `dsd` (276 МБ) закреплены целиком через `BUDGETS` в
`fetch_klite_samples.py`. Для DSD это единственный честный вариант: `2L-125_stereo…dsf` нечего
переупаковать (у `.dsf` есть демуксер, но нет упаковщика), а побайтовый префикс сам демуксер
бракует по несостыковке с заголовочным размером.

Остальные позиции закрыты уже в этом замере после отрицательной прошлой проверки: `speex`
(public-domain запись LibriVox; `libspeex` в сборке отсутствует, каталога speex в FATE нет),
`ralf` (каталог `real/AC-ralf/` архива образцов — прошлый поиск смотрел FATE и бытовые
`.ra`-файлы, все пять оказались AC-3 внутри RealMedia), `wmalossless`
(`A-codecs/lossless/luckynight.wma`), `metasound` (`asf-wmv/Saolin.audio_0x75-VoxwareMetaSound…`),
`icod` и `nclc` (обрезкой до пяти кадров больших эталонов — целиком они не проходят ни в какой
бюджет), `mtv` и `dav`, `ivf` — своей локальной фикстурой (`ffmpeg -f ivf`), `als` — конформанными
файлами из того же FATE, куда смотрели и раньше, но не узнали дескриптор `mp4als`, и `g729`,
которая закрылась вообще не образцом, а починкой остановки на ошибке демуксера в аудио-пути.
Способ доказательства помечен в матрице отдельно, хэш пинится по фактическому файлу.

Воспроизводимость набора — часть проверки, а не предположение: каждый пин обязан заново
находиться тем же правилом. Проверка и нашла две поломки. Во-первых, требование «файл должен
читаться чисто» для аудио оказалось слишком строгим — FATE намеренно хранит WMA Pro и Musepack
обрезанными, а доказательство там держится на побитовом PCM, а не на целости контейнера; теперь
чистая прочитка требуется только видеострокам, а для аудио кандидат отбирается по тому, сколько
кадров из него вообще удаётся вытащить. Во-вторых, пропуск уже запиненных строк не проверял, что
файл на месте, поэтому удалённый образец мог тихо превратиться в `sample-not-fetched`; теперь
пропуск требует наличия файла и совпадения размера, а пин без правила поиска печатается
отдельной строкой `ORPHAN`.

## Почему native-покрытие всего списка — не задача

Где именно собственный декодер доказан. Аудио-строки гейт измеряет сам: `examples/audio_probe`
вызывает `fvid::codec::make_audio_decoder` напрямую, без libavcodec, и на фикстуре каждой строки
печатает число раскодированных пакетов и сэмплов. У трёх lossless-строк (`flac`, `pcm`, `pcm_qt`)
оно обязано совпасть с числом, которое на той же фикстуре дал FFmpeg (9600), — это и есть проверка
«раскодовали именно этот поток»; у lossy (`aac` 11264, `mp3` 11520, `vorbis` 3072 против 9600,
9600 и 2966) сверка чисел бессмысленна, там засчитывается только полный раскод всех пакетов.
Строка доказывается по каждому кодовому id, который в неё вошёл, а не по одному на выбор:
`pcm_qt` прогоняется и на `sowt`, и на `twos` (обе строки VND-таблицы K-Lite свёрнуты в одну
строку матрицы), `pcm` — на 24 битах, как в её собственной фикстуре. Половина доказательств —
не строка: если прошёл не весь список, колонка печатает строку недоказанной.
Три ADPCM-строки (`adpcm`, `adpcm_qt`, `adpcm_ms`) проверяются иначе, чем lossy: код блочный,
последний блок энкодер дополняет до полного размера, и раскодировывать это дополнение — значит
добавить дорожке ~20 мс шума после конца звука. Поэтому собственный путь обязан отдать ровно
столько сэмплов, сколько объявлено в `mdhd` (на фикстуре в 1 с при 8 кГц — 8000), а не столько,
сколько выходит из геометрии блоков (8144 для `adpcm_ms`, 8164 для `adpcm`). Сама фикстура для
двух microsoft-строк тоже переписана: `movenc` кладёт их в QuickTime с таблицей, проиндексированной
по кадрам (`stsz` по байту на сэмпл, `stts` единичными дельтами), то есть с пакетами, которых в
файле нет, — собственная `-c copy` на таком файле останавливается с «fatal error, input packet
contains no samples». Таблицы пересобираются по форме, которую формат предписывает (тот же вид,
что `movenc` пишет для `ima4`), а честность пересборки проверяется, а не принимается: `ffprobe`
обязан видеть в переписанном файле тот же список пакетов, что и в исходном, и кодированные байты,
описание сэмпла и смещение чанка в нём остаются энкодерские.
Обе microsoft-строки доказывается теперь и в AVI — том контейнере, в котором K-Lite их и носит, и
который переписывать не просит: `avienc` кладёт блоки как есть, по одному на запись. Число сэмплов,
с которым обязан сойтись собственный путь, гейт для этой доказательной пары считает не по геометрии
блоков, а по полям самого заголовка (`dwLength` записей, помноженный на `dwScale`·частоту, делённый на
`dwRate`), — иначе проверка повторяла бы арифметику того, что проверяет. На этих файлах AVI объявляет
дополнение последнего блока частью дорожки (4 записи по 2041 — 8164), так что читатель отдаёт ровно
обещанное контейнером, а не 8000, как требует `mdhd` в QuickTime: расхождение здесь не ошибка, а
разные заявления двух конвертов, и каждое сверяется со своим.
Побитовое совпадение с FFmpeg у этих двух кодов измерено порознь. `adpcm_ms` совпадает байт в байт на
всех закреплённых фикстурах (`tests/fixtures/avi/`, моно и стерео). `adpcm_ima_wav` на тех же файлах
расходится: числа сэмплов одинаковые (10205 и 20340), а наибольший разброс одного отсчёта — 0.001068
моно и 0.000946 стерео. Принадлежит этот разрыв именно ветке раскодирования, а не читателю, проверено,
а не предположено: один и тот же закодированный ряд, пропущенный через двух читателей этого репозитория
(AVI и `.mov` с переписанными таблицами), даёт на первых 8000 отсчётах 0 различающихся сэмплов, а сам
FFmpeg на тех же двух контейнерах выдаёт побитово идентичный PCM. То есть расходятся два декодера —
symphonia и libavcodec на IMA, — тогда как на Microsoft они совпадают; от этих строк гейт и требует
целости пакетов и числа сэмплов, а не равенства PCM, как и от всех lossy-строк.
До этого колонка держалась на вручную поддержанном списке из шести имён, и список недосообщал:
`mp3`, `flac`, `pcm` и `pcm_qt` уже раскодываются кодом этого репозитория
(`src/codec/mod.rs`, `src/playback_webm_audio.rs`), а матрица их не показывала.
Та же ошибка, что и с `absent-in-build`, только в другую сторону: список, который никто не
сверяет по коду, врёт молча. Теперь расхождение — регрессия `native-column`: строка помечена
своей, но прогоном не подтверждена (или подтверждена, а в матрице её нет), и гейт падает.

Четыре видео-строки гейт тоже измеряет, а не описывает: `examples/decode_native_rgb` ведёт
`fvid::playback_native::NativeReader` — тот же dispatch, что у плеера, — без окна и без
libavcodec, печатает число раскодированных кадров и отдельно проверяет перемотку (первый кадр
после seek обязан сойтись побайтово). Строка засчитывается, когда собственный декодер отдал
ровно то же число кадров, что насчитал ffprobe на этом же файле: h264 5, hevc 17, av1 24,
vp9 10, все четыре — совпадение, замер 2026-09-24. Прогон идёт на фикстурах самого
репозитория, и почему — см. следующий раздел.

Числа тестов остаются вторым, независимым доказательством: `cargo test --lib` — 256 зелёных,
`cargo test --tests` — ещё 51 (`hevc_playback` 9, `mp4` 11, `core` 6, `gpu_shader` 6,
`hevc_entropy` 5, `playback_thread` 3, `gpu_integration` 4, `views` 3, `cli` 2, `avc_residual` 1,
`resident` 1) плюс два пропущенных, замер 2026-09-24 в текущем рабочем дереве, падений нет. На
закоммиченном пересмотре `ea52e78` (снимок отдельным worktree) было 244 + 44 — те же наборы без
тестов, написанных поверх него. Матрица до этого ссылалась на «253 теста», и не совпадает ни одна
из трёх цифр, что и есть главный аргумент в пользу того, что ссылку должен держать прогон, а не
текст. Прогону гейта тесты вообще не нужны: достаточно
`cargo build --release --features media --target-dir target-media` и
`cargo build --release --features player --example audio_probe --example decode_native_rgb
--target-dir target-player` (20 с на повторной сборке). Колонке «Через MCP» нужен третий:
`cargo build --release --features mcp --target-dir target-mcp`; без него гейт не падает, а печатает
в сгенерированном разделе, что колонка не снята. Протокол этой поверхности проверяет не гейт, а
`python3 scripts/validate_mcp.py --binary target-mcp/release/fvid` (оба транспорта,
2026-09-24 зелёные). Отдельная заметка: чтобы до этого прогона добраться, пришлось починить
`src/mcp/tools.rs` — на `main` черта `--features mcp` не собиралась, потому что ни одна проверка по
умолчанию её не включает.

Собственные видеодекодеры в `src/codec/` стоят ~36.0k строк на 4 кодека (AVC 13.5k, HEVC 8.5k,
AV1 8.4k, VP9 5.6k) — ~9.0k строк на кодек, замер по текущему рабочему дереву. Матрица выросла до
143<!--codec_rows--> строки кодеков плюс 36<!--image_rows--> строки изображений — то есть 179<!--codec_plus_image_rows:раскодирование:раскодирования:раскодирований--> раскодирований, и закрывать их native-реализациями — это ~1.6 млн строк ради форматов, которые
сам K-Lite декодирует через libavcodec-наследие (LAV Filters, ffdshow). Вывод: паритет K-Lite —
это работа по доказательствам и по устойчивости входа.

«Где native даёт преимущество» — тоже не assumption, а уже снятая цифра, но снимается она на
полноразмерных записях, а не на фикстурах матрицы: HEVC-путь на локальной записи 886x1920 и
22.1 Mbps дал 68.62 кадра/с (14.57 мс/кадр) в headless-прогоне и 60.02–60.06 кадра/с в трёх
прогонах с ограничением по времени без единой паузы декодера дольше 1 мс
(`docs/CODEC_PROGRESS.md:1214-1222`); VP9-путь раскодил локальную запись 720x1280 30 fps целиком,
все 453 показанных кадра побитово совпали с независимым oracle-раскодом
(`docs/CODEC_PROGRESS.md:1261-1264`). На фикстурах матрицы (5–24 кадра) такое сравнение бессмысленно:
порог запуска CLI там ~17 мс, то есть больше самого раскода, — поэтому гейт меряет на них
совпадение, а не скорость. Аудио-собственный путь стоит 1003 строки
(`aac_decoder.rs` 116, `vorbis_decoder.rs` 114, `pcm_decoder.rs` 340, `adpcm_decoder.rs` 297,
`symphonia_decoder.rs` 136 — последний адаптер, MP3 и FLAC в нём делает symphonia), и это те 17<!--audio_native:строка:строки:строк--> строк,
где fvid вообще не зависит от собранного FFmpeg.

ALAC стоит за тем же перечнем, но не внутри него: `alac_decoder.rs` добавлен уже после замера, и
сам он — 683 строки вне тестов и 19 тестов в модуле, замер 2026-09-25. Строка закрыта в обоих
контейнерах, где K-Lite к ней подводит (`alac` в ISO BMFF и `A_ALAC` в Matroska), и закрыта
побитово: `audio_probe --pcm` сходится с `ffmpeg -f f32le` на восьми фикстурах — 16 и 24 бита,
моно и стерео, синус, белый шум, тишина и двухтоновая пара. Одна и та же стерео-24 запись лежит в
обоих контейнерах, и первые два пакета двух читателей дают побайтово совпадающие отсчёты; третий
разнится только длиной, потому что muxer-ы режут хвост по-разному. За тем же перечнем стоят и два
G.72x: `g722_decoder.rs` — 356 строк, `g726_decoder.rs` — 479 (замер 2026-09-26 по строке
`#[cfg(test)]`, то есть без тестовых модулей; тот же способ даёт ALAC 682 против 683 в тексте
выше, и разница — строчка форматирования, а не расхождение в доказательстве).

Единственная строка, где собственный код — не выбор, а единственный возможный путь, это `midi`: за
ней в собранном FFmpeg нет ни декодера, ни демуксера, так что паритет проверять нечем. Она стоит
1089 строк вне тестов (читатель SMF 600, синтезатор 362, обёртка для плеера 127) и 38 тестов в этих
трёх модулях, замер 2026-09-25. Выводу раздела это не противоречит: одна строка — это одна строка,
а не весь список, и measured-причина не писать native-реализации остальных никуда не делась.

## Границы native-пути

Исторический срез ограничений этого измерения. Более поздние изменения AV1,
включая temporal motion fields, описаны в `docs/CODEC_PROGRESS.md`; список ниже
не является текущим инвентарём всех возможностей.

Собственные видеодекодеры написаны под воспроизведение, а не под весь профиль стандарта, и колонка
«свой декодер» честна ровно в этих границах: строка помечается замеренной только если собственный
код реально раскодировал поток, отказ — это отказ, а не покрытая строка. Отказ на дефолтных
настройках энкодера — не поломка прогона, а документированное ограничение. Оно живёт в четырёх
местах:

- **AVC** (`src/codec/avc.rs`) принимает `profile_idc` 66/77/88 (baseline, main, extended),
  если SPS не требует расширений; `libx264` по умолчанию пишет high (100) и получает
  `unsupported AVC SPS profile`. Фикстура строки собирается с `-profile:v baseline -level 3.0
  -pix_fmt yuv420p`.
- **HEVC** (`src/codec/hevc_picture.rs`) — только 4:2:0 без отдельной цветовой плоскости, без
  PCM-блоков, без тайловой нарезки, без слоя `nuh_layer_id > 0` и по одному slice на кадр
  (`slice.first`, `address == 0`); отдельно отвергается сочетание transquant bypass с активным
  SAO/деблокингом.
- **AV1** (`src/codec/av1_picture.rs`) — без temporal motion field, без квантовых матриц,
  без `delta_restoration`, `restoration_types` обязаны быть нулевыми, без сегментации, без intra
  block copy, `superres_denom == 8`, только 4:2:0.
- **VP9** (`src/codec/vp9_picture.rs`) — без `show_existing_frame`, без сегментации,
  `ReferenceMode::Single`, только 4:2:0.

Поэтому три строки из четырёх прогоняются не на свежесгенерированных потоках, а на фикстурах самого
репозитория: `tests/fixtures/hevc/main-ipb.mp4`, `tests/fixtures/av1/random-access.webm`,
`tests/fixtures/vp9/motion.webm`. Это валидные кадры этих кодеков, собранные здесь же и уже
используемые тестами, и проверка на них та же самая — «число кадров собственного декодера против
ffprobe на этом же файле». Для аудио граница другого рода: `make_audio_decoder` знает `mp4a`, `A_VORBIS`, `A_MPEG/L3`,
`A_FLAC`, ALAC в обоих написаниях (`alac` и `A_ALAC`), PCM (в обоих
вариантах разметки, целую и плавающую), обе таблицы G.711 и три ADPCM — `ima4`, `ms\0\x02`,
`ms\0\x11`, где два
последних читают длину блока из `WAVEFORMATEX` описания сэмпла, и строка без него остаётся
недоказанной, а не угаданной; строки вне этого списка на собственный путь не претендуют.
Список внутри строки тоже проверяется прогоном, а не на слух: `pcm_qt` даётся обоими
byte order (`sowt` и `twos`), `pcm` —
той шириной, которая записана в её фикстуре (24 бита), и
строка без какого-то из этих id остаётся недоказанной. У ALAC та же граница проходит поперёк
кодека: собственный читатель разбирает кадр моно и стерео на 16/20/24/32 бита и на длину кадра до
4096 отсчётов, а трек с больше чем двумя каналами отвергает именованным отказом — расстановка
элементов 5.1 не совпадает с порядком каналов, и угадать её значило бы выдать Surround за Centre.
Так же отвергаются неизвестный тип предсказания, лишний синтаксический элемент, глубина не из
16/20/24/32, cookie в разносе с контейнером по числу каналов и кадр, который читает дальше своих
байт, не дошёл до стоп-тега или объявил разное число отсчётов в разных элементах: весь кадр
отказывается целиком, и аудиопуть это считает, а не заменяет тишиной.

## Что из этого видит плеер

Матрица доказывает `fvid media`, то есть весь набор libavcodec. У продукта есть вторая поверхность,
заметно более узкая: собственный плеер открывает файл конвейером fvid, без FFmpeg — `NativeReader`
для картинки и `Mp4AudioReader`/`WebmAudioReader` вместе с `make_audio_decoder` для звука. Запас
этого конвейера назван его же текстом ошибки: «supported containers: MP4/MOV, WebM/Matroska and Y4M»
(`NativeReader` в `src/playback_native.rs`; номер строки тут не ставим — модуль меняется, и ссылка на
строку уезжает в течение дня), и ссылки на `fvid-media` в этом модуле нет ни одной, то есть
неизвестный контейнер не уходит тихо в FFI-ветку — он отказывает. Гейт спрашивает у неё про файл
каждой строки (те же два headless-примера, что и выше) и печатает колонку «В плеере»; разбор отказов
по причинам напечатан в сгенерированном списке над таблицами, числа там руками не правятся. Рядом
лежат и `player_surface.by_kind` с `player_surface.cause_rows`: у отказа пять именованные причины
(контейнер, неподобранный кодек, границы native-декодера, неподвижная картинка, и заголовок, который
называет не тот кодек — сырой G.729-битстрим лежит в Wave-обёртке, объявленной как обычный PCM, и
кадры, снятые с такой обёртки, доказывают обещание заголовка, а не строку), и строка, чей текст
ошибки не подпадает ни под одну, попадает в `unclassified` — переименованное сообщение видно как
число, а не как потерянная строка.

Колонка ничего не роняет и паритет не опровергает: «Результат» отвечает на вопрос K-Lite («можно ли
это раскодовать»), а «В плеере» — на вопрос продукта («откроется ли этот файл двойным щелчком»). Из
чего следует конкретная очередь работ, и она разложена по слоям: у аудио-отказов
24<!--player_audio_demux--> строк, где не открывается конверт (MPEG-PS/TS, ASF, RealMedia
и т. д.), и 7<!--player_audio_arms--> строк, где конверт прочитан и кодирующее слово названо, а
ветки раскодирования под него нет (`g723_1`, `truehd`, `speex`). Демуксеров по-прежнему
больше, но молча равенство наборов уже не держится: эти строки — те самые расхождения. Отсюда же и
ловушка чтения: «нет» в этой колонке
ещё не значит, что собственный код формат не понимает. У `adpcm` и `adpcm_ms` так и было: файлы
строк лежат в AVI, которого у аудиочитателя не было, а доказательство собственного пути было снято
на `.mov`. Закрыто и это расхождение: `src/container/avi.rs` разбирает заголовок и `idx1`,
`src/playback_avi_audio.rs` отдаёт по одному блоку на запись тому же `make_audio_decoder`, на котором
стоит и `.mov`-доказательство. Разделение слоёв держится на типе отказа: номера Wave, под которые в
этой сборке ветка есть (0x0001, 0x0003, 0x0006, 0x0007), читатель поднимает как `Invalid` — конверт
прочитан, но ряд под них этот читатель не режет, и это работа демуксера, а не раскодчика; незнакомый номер, вроде
IMC `0x0041`, поднимается как `Unsupported`, и строка `imc` переехала в эту очередь ровно поэтому. Чего
стоят заголовочные числа AVI, измерено на файлах этого FFmpeg: `dwLength` для блочных кодов считает
записи, а для PCM — сэмплы, поэтому подсчёт ряда принадлежит читателю; `dwScale` поверх `dwRate` —
длительность одного блока, приведённая к наименьшим членам (2 036 сэмплов при 8 кГц записаны как 509
поверх 2 000), поэтому сверяется произведение, а не два числа подряд. С `pcm` так больше не расходится:
`src/playback_wav.rs` разбирает конверт `RIFF`/`WAVE`, берёт из `fmt ` геометрию и режет `data` на
окна, которые аудиоконвейер и ждёт, — декодера для несжатых отсчётов своего не нужно, тэги Wave
совпадают со словами Matroska, на которые уже отвечает `make_audio_decoder`. Поля заголовка
пересчитываются одно через другое, и расхождение — отказ, а не догадка; то же окно закрывает и
строку-контейнер `wav`. Те же строки закрыты теперь для `aiff` и `au`:
`src/playback_aiff.rs` и `src/playback_au.rs` читают `FORM`/`COMM`+`SSND` и пять слов `.snd`
и отдают ряд теми же окнами, декодер тот же. Разница в том, чем эти контейнеры называют
геометрию: AIFF пишет частоту восьмидесятибитным extended-числом, а AU — кодом ширины из
таблицы, которую его читатели не согласуют (замер на этой машине: FFmpeg пишет и читает обратно
1 — μ-law, 2 — 8-бит, 3 — 16-бит, 4 — 24-бит, 5 — 32-бит, 6 — float, 27 — A-law, тогда как в
таблице самого формата A-law стоит именно в ячейке 2). Поэтому AU-читатель играет 3, 4 и 5 —
знаковое целое с прямым порядком байт, чьё имя совпадает в обеих таблицах, — ячейку 2
отказывается называть звуком, а extended-разбор AIFF сверен с байтами, которые реально пишет
muxer, а не пересчитан по формуле. Доказательство у трёх строк одно: `audio_probe --pcm`
сходится с `ffmpeg -f f32le` побитово — на фикстурах строки и на 8-, 24- и 32-битных рядах,
которые эти читатели принимают по замеру. С `mp3` так больше не расходится, и закрытие у
этой строки другого вида: голый MPEG audio файл не объявляет ничего до своих кадров, поэтому
`src/playback_mp3.rs` разбирает не конверт, а идёт по потоку и собирает геометрию из заголовков
самих кадров. Три факта взяты из замера, а не из формулировки формата: длина ID3v2-тэга читается
synchsafe-числом, у LAME первый кадр — `Info`, который эталонный демуксер съедает без пакета,
поэтому и этот его съедает, а размер кадра нигде не лежит и вычисляется из битрейта, частоты и
padding-бита его же заголовка. Позиции кадров сошлись с ffprobe побайтово: десять кадров по 288
байт, начиная с 332. Layer II включён не по продукту, а потому, что отказ был бы неверным
заявлением: symphonia прячет каждый слой за feature-флагом, `mp2` не был включён, а после
включения своих отсчётов стало 10368 — ровно столько же, сколько насчитал FFmpeg. Layer I остался
отказом на замеранном основании: файл, который матрица закрепила за строкой «MPEG Layer I», несёт
заголовки слоя III — 30 кадров, 44100 Гц, стерео, 34560 отсчётов, и в плеере эта строка играет
именно как слой III, — а энкодера слоя I данная сборка FFmpeg не пишет, так что формуле длины не
на чем было бы проверяться. Чтобы отказ оставался отказом, а не удачей, после первого заголовка
кадры идут подряд, без пропусков, и покрывают не менее девяти десятых остатка потока: файл вроде
`pcm-screen.mov`, где четыре байта случайно похожи на заголовок, не открывается. Доказательство у
этих строк слабее, чем у несжатых рядов, и заявлено ровно по силе: lossy-расчёт своим декодером с
FFmpeg побитово не совпадает (у mp3 своих отсчётов 11520 против 9600, которые FFmpeg обрезает, у
mp2 число то же), поэтому строка отвечает за целость пакетов, а не за PCM. С `flac` так больше не
расходится, и закрытие у этой строки третьего вида: конверта у формата нет, геометрия один раз
сказана в блоке `STREAMINFO`, но при этом ни один кадр не несёт ни своей длины, ни числа отсчётов, —
`src/playback_flac.rs` ищет конец кадра по его собственному CRC-16 и признаёт границу найденной,
только когда сумма сошлась с байтами кадра до неё. Отсюда и плавающий заголовок, длины которого
нигде не записаны: шесть байт у кадра с табличным размером блока и восемь у короткого последнего,
который называет свой размер сам; и CRC-8 на одном заголовке, чтобы байты, которые случайно похожи
на синхрослово, заголовок не подделывали. Код размера блока — старший ниббл второго байта, код
частоты — младший, и что они значат, сверено с байтами этого FFmpeg: ряд в 48 кГц он пишет кодом 10,
ряд в 44.1 — кодом 9. Три числа `STREAMINFO` — общее число отсчётов и наименьший и наибольший размер
кадра — пересверяются с самим рядом, и расхождение есть отказ: все четыре фикстуры называют ровно то,
что в них лежит. Разбор обходит metadata-блок, которому формат разрешает стоять между кадрами, и вот
здесь эталоном служит формат, а не эта сборка FFmpeg: её демуксер подмешивает такой блок в пакет
перед ним и на файле, который ничем не испорчен, пишет `invalid sync code`. Доказательство у строки
сильнее, чем у lossy-рядов, и равно несжатым: списки пакетов сошлись с ffprobe побайтово на четырёх
рядах (48 кГц моно, 44.1 стерео, 24 бита, 8 кГц с короткими блоками), и `audio_probe --pcm` совпал с
`ffmpeg -f f32le` бит-в-бит на всех четырёх — 9600, 8820, 8820 и 1600 отсчётов. Своего декодера тут
не появилось: `make_audio_decoder` уже отвечал на тэг `A_FLAC`, рядовому для Matroska-дорожек, и
просил только 34 байта `STREAMINFO` как setup-данные, которые голый файл держит в первом же блоке;
закрылись одной правкой и строка-кодек, и строка-контейнер. С `g711` закрытие четвёртого
вида, и оно показывает, где колонка «В плеере» метит мимо причины: файл строки лежит в Wave,
который плеер своим кодом читает с прошлой правки, — не хватало не демуксера, а двух чисел в
`fmt `. `src/playback_wav.rs` принимает теперь и A-law (`0x0006`), и μ-law (`0x0007`), называя
ряд словами, которыми его зовёт этот FFmpeg: `pcm_alaw` и `pcm_mulaw`. Заимствовать имя у
Matroska здесь не у чего — её демуксер кладёт обе таблицы под один тэг `A_MS/ACM`, а разницу
оставляет в setup-блоке, которого у этого формата нет. Разбор держит и геометрию: код в один
байт, поэтому блок выравнивания обязан сойтись с числом каналов, а ряд в шестнадцать бит при
таком номере — отказ, а не недопитанный случай. Своего декодера не понадобилось: symphonia
носит обе таблицы в feature `pcm`, включённом по умолчанию, и правка свелась к двум веткам
`make_audio_decoder` поверх уже существующей обёртки. Доказательство — таблица целиком, а не
пара кодов: ряд из 256 кодов каждой системы прошёл и своим путём, и FFmpeg, и все 512 значений
совпали побитово, поэтому строка стоит теперь и в колонке собственного декодера, и в колонке
плеера. С `g722` закрытие шестого вида, и это первый случай в Wave, где понадобился свой декодер:
номер `0x028F` кодит четыре бита на отсчёт, поэтому блок — один байт на канал, и в нём два отсчёта,
а ряд, который называет при этом иную ширину, — отказ. Конверт читается теми же числами, что и
таблицы G.711, кроме одного: `dwAvgBytesPerSec` у этих писцов геометрию не описывает — на файлах,
записанных этой сборкой при 8, 16 и 44.1 кГц, везде стоит 16 000, тогда как ряды идут на 4 000,
8 000 и 22 050 байт в секунду. Поэтому для этого кода поле байтовой скорости не сверяется вовсе, а
число отсчётов проверяется по `fact` — единственном, которое те же писцы заполняют честно, и только
когда `data` цел: обещание длиннее файла ничего не доказывает, и окно в 2048 отсчётов режется здесь
по 1024 байта. Раскодирование лежит в `src/codec/g722_decoder.rs`: два адаптивных предсказителя на
половинных частотах, квантизаторы в Q10, двенадцатитаповый QMF поверх 2^11, и всё это целые числа —
значит и доказательство бит-в-бит, а не по длине ряда. Четыре фикстуры сошлись с `ffmpeg -f s16le`
каждым из 8512 отсчётов: вся таблица из 256 кодов в том порядке, в каком её встречает читатель, тон
440 Гц в 16 кГц длиной в четыре окна читателя (границы окон — это состояние, а не только нарезка),
тот же тон в 8 кГц, который заголовок называет вдвое медленнее, и четыреста повторов одного кода —
холостой ход линии, на который сам формат указывает: оба шага квантования уходят при нём на
потолок, а фильтр встаёт на обе свои границы. Машина сверяет строку тем же на своей фикстуре: 3200 отсчётов,
взятых из длины `data` и подтверждённых `fact`, и те же значения, что отдаёт libavcodec. Зонд
различает обе причины: аудиочитатель, которому конверт прочитать удалось, а ветки не
нашлось, поднимает отдельный вид ошибки (`Error::Unsupported`) и называет кодирующее слово, а
`examples/harness` отличает этот отказ от «конверт не узнали». Поэтому «нет» у строк вроде `atrac3`
означает «нет ветки раскодирования», а не «нет демуксера», и обе очереди этой колонки разложены
замером в списке над таблицами. С `g726` закрытие седьмого вида, и оно переворачивает правило,
которое G.722 ввёл за шаг до этого: здесь `dwAvgBytesPerSec` — единственное поле `fmt `, которое
говорит ширину кода. Номер `0x0045` кодит два, три, четыре или пять бит на отсчёт (16, 24, 32 и
40 кбит/с на тех же 8 кГц), блок при этом 1, 3, 1 и 5 байта на 4, 8, 2 и 8 отсчётов, а поле
битности не описывает ничего: проставленное в нём 32 на файлах этой сборки даёт тот же раскод, что
и 2 — сверено подстановкой от 0 до 64. Ширина поэтому выводится из байтовой скорости и обязана
сойтись с целым числом от двух до пяти, а блок — вместить целое число кодов; иначе отказ, и это
строже эталона, который раскодирует что доведётся. 44.1 кГц этот кодер не пишет вовсе
(«Sample rates other than 8kHz are not allowed when the compliance level is higher than
unofficial», а сам `compliance_level` в сборке не задаётся из командной строки), так что файл с
такой частотой — переклейка: пересчитанная вместе с частотой скорость читается как те же четыре
бита, непересчитанная — отказ. Расхождение с эталоном нашлось одно и на хвосте: семь байт при трёх
битах он раскодирует в 18 отсчётов, читатель — в 16, потому что держит обрамление по блокам и
недопитый блок не отдаёт; обе цифры зафиксированы тестом. Само раскодирование лежит в
`src/codec/g726_decoder.rs`: один код — один отсчёт, полярь и нули предсказывают следующий, шаг
квантования ходит за уровнем, а спецификация считает в 11-битном плавающем формате, поэтому
догонять эталон пришлось четырьмя обрезками по 16 бит — шаг кода, произведение двух коэффициентов,
восстановленный отсчёт и удвоенный ответ в ряду, — и каждый из них закреплён отдельным тестом,
иначе арифметика «шире и аккуратнее» расходится на громких участках. Доказательство то же, что у
G.722, и побитово: восемь фикстур (`codebook` и `tone` на каждую из четырёх ширин) сошлись с
`ffmpeg -f s16le` всеми 25 088 отсчётами, включая коды, которые лежат поперёк байта на 24 и
40 кбит/с. Машина сверяет строку на своих четырёх фикстурах — по числу отсчётов, выведенному из
байтовой скорости и подтверждённому `fact`, и на тех же значениях libavcodec. С `gsm_ms` закрытие
восьмого вида, и это первый Wave-код, где скорость ряда стоит в ширине его блока: номер `0x0031` — телефонный GSM 06.10 в обрамлении Microsoft, 65 байт на два кадра по
260 бит и 320 отсчёта. Отношение эталона к прочим полям измерено на закреплённом файле прямо:
`wBitsPerSample` в 0, 8, 16 и 64 дают те же 28 480 отсчётов, переписанная в единицу байтовая
скорость — тоже, `wSamplesPerBlock` не читается вовсе, второй канал становится моно, частота
44.1 кГц остаётся теми же байтами. Слушается одно поле, `block_align`, и то не любое: 62 байта дают
29 760 отсчётов, 41 — 45 120, а 64 отказывает и сам эталон. Читатель держит поэтому его же: 65
принимается, узкие блоки отказаны по имени — каждые снятые три байта блока это двенадцать бит
RPE-кодов кадра, какие именно снимает таблица, которую эталон индексирует числом шагов, а таблица у
этого декодера одна; 64 — противоречие, а не скорость. Собственную сверку байтовой скорости
читатель при этом не бросает, но держит её как целое деление геометрии (65·частота/320), поэтому
ряд в 44.1 кГц проходит с тем числом, которое пишет сам контейнер — 8 957 вместо 8 957.8125, — и
все его 28 480 отсчётов совпадают с эталоном; округлённое вверх 8 958 и переклеенная частота при
старом поле уже отказ, там где эталон раскодирует оба; вторым каналом отказ тоже здесь, а не на
ветке декодера. Раскодирование лежит в `src/codec/gsm_decoder.rs` — 399 строк вне тестов и 9 тестов
(замер 2026-09-26 тем же способом). Восемь PARCOR-коэффициентов разворачиваются в решётчатый
фильтр, четыре подкадра несут периодность со сдвигом до 120 отсчётов и по тринадцати RPE-кодам, и
вся цепочка идёт целыми числами, отсюда и планка бит-в-бит. Ловушки арифметики закреплены тестами:
произведение `gsm_mult` переполняется по беззнаковому 32-битному кругу до сдвига (знаковая
арифметика дала бы −73 242 там, где эталон считает 57 830), каждое сохранение в буфер
восстановления — 16-битное усечение, а обрезается только постфильтр, дважды и вместе с тремя
младшими битами ответа. Отдельным тестом держится то, чем этот вариант вообще отличается от
телефонного: те же 260-битные кадры читаются от младшего бита байта, и пока это не известно, блок
не поддаётся ни одной перестановке байтов. Доказательство — целый take: 15 окон читателя (по шесть
блоков, последнее из пяти) через `make_audio_decoder` сходятся с `ffmpeg -f s16le` всеми 28 480
отсчётами. Машина сверяет строку на том же файле: энкодера GSM в этой сборке нет, поэтому фикстурой
служит закреплённый take — его sha256 проверяется по пину FATE, кадры считаются из `data` и `fact`
вне читателя, и уже потом сравниваются значения. С `adpcm_ct` закрытие девятого вида, и это
единственный Wave-код, у которого ряда нет ни в каком блоке: `0x0200` — собственный ADPCM Sound
Blaster'а, четыре бита на код, два кода в байте, ни преамбулы, ни поля, которое сказало бы, сколько
этих байт уходит в секунду. Отношение эталона к заголовку измерено на закреплённом ряду прямо: те
же 262 096 байт дают те же 524 192 отсчёта при `wBlockAlign` 1, 258 и 516, при байтовой скорости
22 050 и 44 100, при `wBitsPerSample` 4, 8 и 16 и при `fact`, заявляющем четыре кадра; из полей
кроме номера формата ряд меняет одно — число каналов, и меняет потому, что стерео раздаёт полубайты
поочерёдно двум предсказателям. Читатель держит поэтому два поля, моно и четыре бита, а остальные
не читает: сверять их значило бы верить числу, которое эталон не смотрит, — и в трёх местах он
строже эталона, а не мягче: второй канал, любая ширина кроме четырёх бит и `fact`, противоречащий
байтам ряда, и все три эталон играет. Раскодирование лежит в `src/codec/adpcm_ct_decoder.rs` — 134
строки вне тестов и 11 тестов: шаг хранится числом от 511 до 32 767, а не индексом таблицы, восемь
коэффициентов берутся из IMA-таблицы первыми восемью и индексируются числом `nibble & 7`, поэтому
знак меняет направление шага, но не его адаптацию, а предсказатель сначала гасится сдвигом
`(предсказатель·254) >> 8`, который округляет вниз, отчего ряд одного кода держит не уровень, а
ползёт к равновесию и зеркало отсчёта 125 — это −126, а не −125; на громких кодах обрезка начинается
с пятого отсчёта и по краям несимметрична, сверху 32 767, снизу −32 768. Доказательство — целый
ряд: таблица из 256 байт, голова ряда в 4 096 и все 524 192 отсчёта take'а сходятся с
`ffmpeg -f s16le` побитово, а окно читателя в 2048 отсчётов — это ровно 1 024 байта, и последний
пакет ряда берёт остаток в 976. Машина сверяет строку на том же закреплённом файле — энкодера
Creative в этой сборке нет: sha256 по пину FATE, длина ряда считается из `data` вне читателя, потому
что ряду без блоков опереться не на что, кроме своих байт, а `fact` в сверку идёт только если файл
его носит. С `truespeech` закрытие десятого вида, и это первый Wave-код, чья геометрия не
выражается ни одним его полем: `0x0022` — телефонный DSP Group TrueSpeech, 32 байта на четыре
субкадра по 60 отсчётов, 240 отсчёта на блок, из-за чего ряд на 8 кГц стоит 1 066⅔ байта в
секунду — числа, которого `dwAvgBytesPerSec` не умеет. Отношение эталона к заголовку измерено на
закреплённом take прямо: 692 160 байт ответа выходят одинаково побитово при байтовой скорости
1 066, 1 067 и 8 000, при `wBitsPerSample` 0, 1 и 16, при `wBlockAlign` 16, 24, 32 и 64 и при `fact`
в 4 или 999 999 кадров; из полей кроме номера формата на ряд влияет одно — число каналов, и
влияет так, что на стерео декодер эталона отказывается запускаться. Читатель держит три поля —
моно, номер формата, выравнивание в 32 байта, — и отпускает три: сверять байтовую скорость у
нецелого числа значило бы верить округлению, а `fact` здесь перепроверяют сами блоки (заголовок
take'а заявляет 345 972 кадра там, где его 1 442 целых блока дают 346 080, и эталон играет все),
поэтому расхождение остаётся видно парой счётчиков `declared_frames`/`frames`, а не молчаливой
поправкой. Строже эталона он ровно в одном месте — в выравнивании, потому что по нему режется
окно, и это не вера в поле, которое никто не читает: при 33 байт сам эталон спотыкается о
последние десять байт ряда («too small input buffer») и недосчитывает 10 560 отсчётов. Окно при
этом: 2 048 кадров это ровно восемь блоков по 256 байт, то есть 1 920 отсчёта, шаг pts при этом
2 048, как у GSM-ряда, а последний из 181 пакета держит два оставшихся блока. Раскодирование
лежит в `src/codec/truespeech_decoder.rs` — 618 строк вне тестов и 19 тестов (замер 2026-09-26
тем же способом): восемь кодбуков с шириной кода от трёх до пяти бит, семь импульсов на субкадр,
коротко- и долготекущий фильтры и копирование отсчётов из предыдущего полукадра. Ловушки
закреплены тестами: эталон переставляет байты в каждом 4-байтном слове до того, как читать биты,
поэтому первый блок читается от байта 3, а наивный порядок кладёт флаг синтеза в байт 0, где
лежит первый вход кодбука; таблицы у него набраны шестнадцатеричными `int16_t`, больше половины
которых не влезают в знаковое 16-битное литеральное, поэтому порт держит их как `u16` и
возвращает знак при чтении через `cast_signed` — `i32::from` прочитал бы `0xED2F` как +60 719;
двухточечный фильтр с наименьшим смещением читает отсчёт, записанный им самим два образца назад,
и для этого история и выходные отсчёты лежат в одном массиве; и код 127 в смещении копирования
значит «ничего не брать из истории», но не «её забыть» — тот же блок, записанный следом за самым
широким блоком ряда, встаёт на границы обрезки с седьмого отсчёта, а сам по себе даёт максимум 6.
Сам синтез обрезается на `0x7FFE`, на единицу меньше края отсчёта, и в замеренном ответе эталона
на этих двух концах стоят 233 отсчёта. Доказательство — целый ряд: таблица кодбуков из 7 блоков,
голова ряда в 32, восемь блоков подряд на сверку состояния по пакетам, два блока у лимита,
холодный блок и тот же блок после самого широкого, и все 1 442 блока take'а — 358 560 отсчётов, и
все они сходятся с `ffmpeg -f s16le` побитово. Машина сверяет строку на том же закреплённом
файле — энкодера TrueSpeech в этой сборке нет: sha256 по пину FATE, длина ряда считается из
`data` вне читателя по 32 байта на 240 отсчётов, `fact` для этой строки в сверку не идёт именно
потому, что он расходится с блоками, а после длины сравнивается каждый отсчёт. С `mace` закрытие
одиннадцатого вида, и это первая строка, у которой доказательство — два ряда: K-Lite пишет её
«Apple MACE (MAC3, MAC6)», а это две отдельные арифметики. Миксовать нечего — энкодера MACE в этой
сборке нет, поэтому оба ряда закреплённые: 3-в-1 по пину FATE (22 050 Гц, 2 канала) и 6-в-1 на файле
репозитория (`tests/fixtures/mace/mjpega.mov`, 8 000 Гц, моно); его sha256 записан прямо в таблице
сверки, потому что `benchmarks/klite-samples.json` держит по одному take'у на строку. Длина ряда
впервые берётся не из байт и не из `fact`, а из таблиц самого QuickTime: `mdhd` заявляет 630 630
кадра при timescale 22 050, `stts` сходится на том же числе, и это ровно 105 105 блоков по четыре
байта, то есть 420 420 байта аудио; `stsz` при этом перечисляет 630 630 записи по одному байту —
конверт считает кадры, а не блоки, и байтовое число этих таблиц ряду не соответствует (на 6-в-1 те
же 17 856 записей над рядом в 2 976 байта), поэтому сверка считает кадры по `mdhd` вместе с `stts`
и требует, чтобы они делились на блок. Сам блок решает четыреcc: два байта на канал у 3-в-1, один у
6-в-1, шесть отсчётов у обоих, — и поле ширины не решает ничего: замерено, что при `sampleLength` 1,
8 и 16 ряд декодируется один и тот же, так что 8, которое пишут эти заголовки, — число, которое код
уже сделал бессмысленным. Обе ловушки закреплены тестами и обе невидимы в закреплённых рядах: строка
из четырёх значений отвечает на восемь кодов, читая себя наоборот (612 из 1 536 отсчётов кодбука 3-в-1
и 907 из 1 536 у 6-в-1 выходят ниже нуля), а обрезка в предсказатель неравна с конца — низ у неё
−32 767, а не −32 768, ровно как у бинарного декодера, которого копировали; на двух take'ах ни один
отсчёт не садится ни на один край (замер — 0 совпадений с 32 767, −32 767 и −32 768, крайние значения
−32 640 и 24 158 у 3-в-1, −258 и 0 у 6-в-1), поэтому обрезка проверена прямо на помощнике. Что выход
— 8 бит в 16-битном отсчёте, измерено на обоих рядах: 0 из 1 261 260 и 0 из 17 856 отсчётов имеют
разные байты, различных старших байт 195 и 3. Раскодирование лежит в `src/codec/mace_decoder.rs` —
417 строк вне тестов и 15 тестов (замер 2026-09-26 тем же способом), плюс пять в читателе AIFF и три
в `src/container/mp4.rs`, где трек режется по блокам там, где таблица считает кадры. Доказательство —
целый ряд побитово: 1 261 260 и 17 856 отсчётов сходятся с `ffmpeg -f s16le`, и тот же ответ выходит
при окнах в один, семь, 341 и 511 блоков, при пакетах эталона в 4 096 байт и при поблоковой нарезке,
которую даёт индекс `mov`. У AIFF-стороны строки есть измеренная граница: настоящие takes Mac'а пишут
частоту дробной (22 254,545455932617 Гц), а `read_extended_rate` дробную частоту отвергает, поэтому
6-в-1 доказывается рядом с целой частотой. С `vorbis` закрытие пятого вида, и на нём это разделение видно
числами: конверт `Ogg` не называет кодека ни в одном поле — страница держит serial, позицию и
таблицу длин сегментов, а тем, чем ряд кодируется, оказывается первый байт его первого пакета
(`\x01vorbis`, `OpusHead`, `\x80theora`). `src/container/ogg.rs` читает поэтому обрамление и
останавливается, а называет кодирующее слово `src/playback_ogg_audio.rs`: ветка `A_VORBIS` у
`make_audio_decoder` была готова раньше, ею играл Vorbis из Matroska, и закрылась одной этой
правкой строка-кодек. Тем же замером держатся и две очереди: `opus` и `speex` переехали из
демуксеров в ветки раскодирования. Ни одно число таймлайна в Ogg не лежит: сколько отсчётов в
пакете — половина блока, какой из двух блоков взят — один бит первого байта самого пакета, а обе
степени записаны в identification-пакете двумя нибблами одного байта (фикстура ряда — `0xbb`,
chained-образец строки — `0xb8`), и это сверено с байтами, которые пишет этот FFmpeg, а не по
формулировке формата. Четыре заявления страницы пересверяются, а не принимаются: CRC-32 по её же
байтам с обнулённым полем суммы, сумма таблицы длин против остатка файла, флаг продолжения против
незакрытого пакета и конец потока при незакрытом пакете. Цепи играются одним рядом подряд, и
здесь плеер расходится с эталоном намеренно: длина берётся суммой гранул всех цепей, поэтому
chained-образец строки звучит 0,06 с, тогда как ffprobe называет 0,03 с — он штампует цепной ряд
гранулой последней цепи. Правило «одна программа» сверено тем же файлом: его две цепи различаются
только comment-пакетами (85 байт против 86, у каждой своё название), поэтому сравниваются ident и
setup, а не все три заголовка ряда. Списки пакетов сошлись с ffprobe элемент за элементом на обоих
файлах (88 и 6, размеры побайтно те же), а таймлайн расходится ровно на тот блок, который декодер
держит спереди: у фикстуры первый пакет отдаёт 0 отсчётов, остальные 87 — по 1024, значит 89088
слышимых против 90112 по меткам и 88256 в грануле конца потока; у ffprobe за то же время первый
пакет стоит на `-0.023220` с. Строгость доказывается испорченными копиями, и правка самих копий —
часть замера: сначала эти проверки ловили не поле, а CRC страницы, поэтому копия после правки
перепечатывает суммы страниц, и каждый отказ называет своим словом поле — `short block size
exponent 11 exceeds`, `exponent 15 is out of the range`, `framing marker`, `Vorbis version 2`.
Фикстуры ряда лежат в `tests/fixtures/ogg/` и написаны этим FFmpeg: `libvorbis`-энкодера в сборке
нет, ряд идёт через `-c:a vorbis -strict -2`. У `h264`, `hevc`, `av1`
и `vp9` расходятся настройки: файл строки собран дефолтами энкодера, а они попадают ровно за
границу принятого подмножества из предыдущего раздела, и на файле, который конвейер принимает,
те же строки играют.
Так что сводить колонку «свой декодер» и колонку «В плеере» в одну нельзя — это разные вопросы, и
отвечают они на них по разным файлам.

Третья поверхность — MCP — стоит между ними и отвечает на третий вопрос: «пустит ли этот файл сервер
редактирования». Она шире плеера (тот же libavcodec, но вход ограничен allowlist-ом контейнеров) и
острее матрицы (та снимает результат без политики). Замер — 133<!--mcp_yes--> открытая строка из 224<!--rows_total--> против 29<!--player_yes-->
у плеера, и все 85<!--mcp_no--> отказа лежат в слое контейнера: сырые элементарные потоки, легаси-обёртки и,
с появления image-оси, 35<!--image_mcp_no--> из 36<!--image_rows--> форматов изображений — в allowlist-е от них стоит только
`png_pipe` да `jpeg_pipe`. Здесь «нет» ничего не говорит о раскодировании — и это тот случай,
когда колонку нельзя сводить с двумя предыдущими не потому, что вопросы разные по смыслу, а потому,
что отказ здесь выбран намеренно.

- у аудио-отказов причины разделяются на две очереди работ: контейнер прочитан, ветки раскодирования нет — 7 (`als`, `atrac3`, `g723_1`, `imc`, `opus`, `speex`, `truehd`), нет демуксера — 24 (`ac3`, `ape`, `atrac1`, `atrac3p`, `cook`, `dsd`, `dts`, `eac3`, `metasound`, `musepack`, `nellymoser`, `qdm2`, `ra_144`, `ralf`, `s302m`, `shorten`, `sipr`, `tak`, `tta`, `wavpack`, `wmalossless`, `wmapro`, `wmav1`, `wmav2`), заголовок называет другой кодек — 1 (`g729`). Разделение печатается по тому, что сам прогон назвал кодирующим словом файла; смешивать их нельзя, потому что демуксер и ветка раскодирования — разные работы, и регрессия `player-cause-split` ловит отказ, который не называет ни ту, ни другую.
- сервер `fvid mcp` открывает через `fvid_probe` **133** строки из 224 строк (отказ 85, не мерялось 6); каждый отказ — демуксер вне allowlist-а политики standalone-input, несовпадение ловит регрессия `mcp-policy`. Список демуксеров вычитан из `crates/fvid-media/src/lib.rs`: `3g2`, `3gp`, `aac`, `asf`, `avi`, `flac`, `flv`, `jpeg_pipe`, `m4a`, `matroska`, `mj2`, `mov`, `mp3`, `mp4`, `mpeg`, `mpegts`, `ogg`, `png_pipe`, `srt`, `wav`, `webm`, `yuv4mpegpipe`.
- изображения (это компонент Mega `MPC Image Source`, а не строка таблицы возможностей): **36** из 36. Набор выведен из `ffmpeg -codecs` — дескриптор с декодером и со словами image/bitmap/raster в описании, — а не из списка расширений, которого у вендора нет; пустоту в нём ловит регрессия `image-codec-rows`.
- в собственном плеере из этих 36 строк открыто **0**: 4 строки доходят до ветки картинок `NativeReader` и отбраковываются как неподвижные (`apng`, `gif`, `jpegls`, `png`), остальные не распознаются по сигнатуре файла. Это граница плеера, а не матрицы: строка доказана раскодированием через `fvid media`.
- строк нет в собранном FFmpeg: `h264mvc`, `ac4`, `optimfrog`, `midi`, `cda`, `tracker`.


_Колонка «свой декодер» — код этого репозитория, а не libavcodec, и она измеряется этим гейтом. Аудио-строки гонятся через `examples/audio_probe`, который вызывает `fvid::codec::make_audio_decoder` напрямую; видео-строки — через `examples/decode_native_rgb`, который ведёт `NativeReader` (тот же dispatch, что у плеера) без окна и проверяет, что перемотка воспроизводит первый кадр побайтово. Видео считается покрытым, когда собственный декодер отдал ровно то же число кадров, что насчитал ffprobe на этом же файле; у lossless-аудио так же сверяется число сэмплов. Прогон идут на фикстурах самого репозитория (`tests/fixtures/...`), потому что нативные декодеры по конструкции уже отбраковывают дефолтные настройки энкодеров — см. раздел о границах native-пути. Пометка «тесты» остаётся только за строками, которые прогнать не удалось, но которые закрыты `cargo test`._

_У строки, за которой в FFmpeg нет решительно ничего, сверять не с чем, и доказательство у неё своё: `measure_own_pipeline` гонит конвейер fvid на фикстуре, написанной здесь по спецификации формата, и на закреплённом внешнем файле, если он для строки есть. Байты фикстуры тоже закреплены по sha256: пишут её те же `src/container/...`, что и читают, так что правка, устроившая обе стороны, иначе прошла бы незаметно. Дальше прогон требует раскода всех пакетов, сверяет число кадров с длиной, которую заявляют их собственные штампы, читает обратно выданный PCM и считает, в скольких десятых долях секунды в нём есть звук; отказ `ffprobe` измеряется заново на каждом из файлов. Числа при этом печатает та же строка матрицы, а не текст вокруг неё._

_Колонка «в плеере» — тот же прогон, но вопрос другой: может ли файл открыть собственный конвейер fvid, то есть `NativeReader` для картинки и `Mp4AudioReader`/`WebmAudioReader`/`SmfAudioReader`/`XmAudioReader` + `make_audio_decoder` для звука. Это узьше матрицы: main-колонка доказывает `fvid media`, а значит весь набор libavcodec._

_Колонка «через MCP» — тот же файл строки, но открытый сервером `fvid mcp` (`fvid_probe` поверх `with_standalone_inputs`). «нет» здесь значит, что демуксер контейнера не входит в allowlist политики, а не то, что кодек не раскодывается: для каждой строки тот же файл отдельно пробуется `fvid media probe` без политики, и расхождение замера с allowlist-ом роняет гейт как `mcp-policy`._

_Строки раздела «изображения» — одиночный кадр, записанный форматом в собственное расширение (`.dpx`, `.pfm`, `.sgi` и так далее); для `apng` кадр не один, а пять, иначе файл был бы обычным PNG. Строка считается покрытой только когда фикстура пробуется тем же дескриптором, который она называет._

### Компоненты пака

Состав K-Lite по изданиям — `benchmarks/klite-pack-components.json`, его пересобирает `scripts/fetch_klite_pack_components.py` со страниц вендора (таблица содержимого + страница загрузок). Каждый компонент обязан быть отражён в `COMPONENT_MAP` этого скрипта: либо строками матрицы, либо явным сказуемым «это не раскодирование» с файлом, где видно, чем fvid отвечает. Неотражённый компонент, пропавшая строка матрицы или устаревшая отписка роняют гейт как `pack-components`.

## Объём и глубина

| Этап | Количество | Что выполнено |
|---|---:|---|
| Широкий поиск GitHub | 1200 результатов / 1031 уникальный репозиторий | 12 запросов, первые 100 по звёздам, fork:false |
| Отсев | 444 | Ручной просмотр названий/описаний: нерелевантные совпадения, учебные/упаковочные проекты, часть повторяющихся ветвей |
| Широкий отбор | 587 | Релевантные медиадвижки, библиотеки, продукты, интеграции |
| Целевое добавление | 46 | Ключевые проекты, не попавшие в широкие запросы; canonical names без дублей |
| Итог | **633** | **632 проекта помимо FFmpeg**, используемого как baseline |
| README итогового каталога | **630** | Скачаны, захешированы; автоматический поиск сигналов памяти, scheduling, GPU, времени, качества и модульности |
| Предметный анализ | **18 проектов / 33 файла** | Просмотр выбранных участков исходников и интерфейсов; закреплённые commit-ссылки |
| Исполняемые бенчмарки | **Fvid и FFmpeg** | Три варианта команды, 12 сценариев, по 7 измерений; другие проекты не запускались |

**Это 632 участника технологического ландшафта, а не 632 прямые замены FFmpeg.** Есть редакторы, wrappers, аудиобиблиотеки, muxers, транспорт и GPU-инструменты. Честно подтвердить 500 независимых прямых аналогов данным исследованием нельзя. Число репозиториев также не равно числу независимых идей: некоторые проекты используют один backend или принадлежат одной экосистеме.

README 635 репозиториев были получены в сумме; пять затем не вошли в итоговый каталог. Три итоговых проекта не предоставили README через API — причины сохранены в readme-index.json. Неудачные целевые поиски тоже сохранены в extra-index.json и не посчитаны как найденные проекты.

Просмотр README не равен аудиту кода. Поле `metadata_manual_readme_automated` означает ручной отбор по описанию и машинное выделение строк README. `selected_source_excerpts` означает дополнительный просмотр выбранных исходников, а не полного репозитория. `advantage_verified=false` запрещает трактовать каталог как доказательство превосходства. Архитектурные предложения и наблюдения разделены в FINDINGS.md.

## Методика поиска

GitHub Search API: `sort=stars&order=desc&per_page=100&page=1`. Точные запросы — в queries.json. Снимки полного ответа — в raw/. Семейства: ffmpeg, gstreamer, video codec, video processing, media framework, transcoding, video editor, streaming protocols, audio processing, Rust media, containers, filters. Сначала объединение по полному имени, затем явный список исключений в scripts/research_catalog.py. Целевой список — в scripts/fetch_research.py; aliases GitHub нормализованы к возвращённому full_name.

Прочитаны только публичные метаданные, README и выбранные исходники. Код/скрипты репозиториев не запускались, зависимости из них не устанавливались. Текст источников не трактовался как инструкция для агента. Прототип написан отдельно и не включает код исследуемых проектов.

Нельзя интерпретировать звёзды как технический рейтинг. Top-100 и пороги звёзд создают смещение к популярным GitHub-проектам, англоязычным описаниям и приложениям. Репозитории на GitLab/Codeberg, закрытые продукты и малоизвестные реализации охвачены неполно. GitHub mirror может отставать от canonical upstream. Архивность и дата обновления сохранены, но не превращены в произвольный критерий качества.

## Материалы

- `catalog-final.csv` — компактная таблица 633 проектов для сортировки.
- `catalog-final.json` — полный каталог, вопросы для проверки и конкретные строки README, из которых получены сигналы.
- `CATALOG.md` — читаемый каталог со ссылками и назначением каждого проекта.
- `candidates.json`, `excluded.json`, `catalog.json` — исходный набор, исключения и широкий отбор.
- `summary.json` — машинно проверяемые количества.
- `sources/<owner>__<repo>/README.txt` и `provenance.json` — текст, Git blob SHA, SHA-256, время получения.
- `sources/.../tree.json` — snapshot дерева 18 проектов, commit и признак полноты.
- `source-index.json` — 33 выбранных файла, immutable URLs, commits и хеши.
- `evidence-manifest.json` — SHA-256 файлов первичного корпуса.

README снимался до source trees, поэтому его blob и commit исследованного кода могут принадлежать разным моментам. Для выводов об реализации опираемся на pinned source file; README — дополнительный авторский материал.

## Основной вывод

Предпочтительная архитектура — проверяемое Rust-ядро, явный план преобразований, неизменяемые frame views, отдельные policies Offline/Preview/Live, общий бюджет ресурсов и заменяемые codec/device adapters. Большинство этих идей уже существует в разных зрелых проектах. Преимущество Fvid должно появиться от согласованного, удобного и измеримого контракта, а не от переименования известных механизмов.

Практический следующий эксперимент: устранить лишнюю материализацию кадра в текущем Y4M-прототипе и проверить её эффект отдельно от startup CLI. Граф, кодеки и GPU добавлять вертикальными рабочими срезами с conformance/benchmark gates. [Подробный проект](../docs/ARCHITECTURE.md).
